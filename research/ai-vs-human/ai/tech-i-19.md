# JWT (JSON Web Token)

## 1. 개요

JWT는 **당사자 간에 정보를 JSON 객체로 안전하게 주고받기 위한 개방형 표준(RFC 7519)**입니다. 주로 **인증(Authentication)**과 **인가(Authorization)**에 쓰입니다. 토큰 안에 사용자 정보와 권한이 들어 있어서, 서버가 세션 저장소를 조회하지 않고도 요청한 사용자를 확인할 수 있습니다. 이런 특성 때문에 **Stateless 인증 방식**의 대표 기술로 꼽힙니다.

---

## 2. 구조

JWT는 `.`으로 구분된 세 부분으로 이루어지며, 각 부분은 **Base64URL**로 인코딩됩니다.

```
xxxxx.yyyyy.zzzzz
Header.Payload.Signature
```

### ① Header
- 토큰 타입(`typ`)과 서명 알고리즘(`alg`)을 담습니다.
```json
{ "alg": "HS256", "typ": "JWT" }
```

### ② Payload
- 실제로 전달할 데이터인 **Claim**을 담습니다.
- **Registered Claim**: `iss`(발급자), `sub`(주제), `aud`(대상), `exp`(만료 시간), `iat`(발급 시간), `nbf`(활성 시작 시간) 등
- **Public / Private Claim**: 서비스에서 직접 정의하는 값(예: `userId`, `role`)
- ⚠️ Payload는 **암호화되지 않고 인코딩만** 됩니다. 비밀번호 같은 민감한 정보는 절대 넣으면 안 됩니다.

### ③ Signature
- `Header + "." + Payload`를 비밀 키로 서명한 값입니다.
- 토큰이 **위조나 변조되지 않았는지 검증**하는 데 씁니다.
```
HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secret)
```

---

## 3. 서명 알고리즘

| 구분 | 알고리즘 | 특징 |
|---|---|---|
| 대칭키 | HS256 | 같은 비밀 키로 서명과 검증을 함. 빠르지만 키를 공유해야 함 |
| 비대칭키 | RS256, ES256 | Private Key로 서명하고 Public Key로 검증. MSA 환경에 적합 |

---

## 4. 인증 흐름

1. 클라이언트가 ID와 비밀번호로 로그인을 요청합니다.
2. 서버가 사용자를 확인한 뒤 JWT를 발급합니다.
3. 클라이언트는 토큰을 저장하고, 이후 요청마다 `Authorization: Bearer <token>` 헤더에 담아 보냅니다.
4. 서버는 서명과 만료 시간을 검증한 뒤 요청을 처리합니다.

---

## 5. 장단점

### 장점
- **Stateless**: 서버에 세션을 저장할 필요가 없어 **수평 확장(Scale-out)**이 쉽습니다.
- **자가 수용적(Self-contained)**: 토큰 자체에 필요한 정보가 들어 있어 DB 조회가 줄어듭니다.
- 여러 도메인이나 서비스에서 함께 쓰기 좋아 **MSA나 모바일 환경**에 적합합니다.

### 단점
- **토큰 무효화가 어렵습니다**: 한 번 발급하면 만료 전까지 강제로 폐기하기 어렵습니다.
- 세션 ID보다 **크기가 커서** 요청마다 네트워크 부담이 늘어납니다.
- Payload가 노출되므로 **민감 정보를 담을 수 없습니다**.
- 토큰을 탈취당하면 만료될 때까지 악용될 수 있습니다.

---

## 6. Access Token과 Refresh Token

탈취 위험과 사용자 편의를 함께 고려하려고 **두 가지 토큰**을 나누어 씁니다.

- **Access Token**: 만료 시간을 짧게(15분~1시간) 잡고, API 요청에 사용합니다.
- **Refresh Token**: 만료 시간을 길게(2주 등) 잡고, Access Token을 다시 발급받을 때만 사용합니다. 서버 DB나 Redis에 저장해 관리합니다.
- **Refresh Token Rotation**: 재발급할 때마다 Refresh Token도 새로 바꿔 재사용 공격을 막습니다.

---

## 7. 보안 고려사항

- **저장 위치**
  - `localStorage`: **XSS 공격**에 취약합니다.
  - `HttpOnly + Secure Cookie`: XSS는 막을 수 있지만 **CSRF** 대비가 필요합니다(`SameSite` 속성 사용).
- 반드시 **HTTPS**를 사용해야 합니다.
- `alg: none` 공격을 막으려면 서버에서 **허용할 알고리즘을 명시**합니다.
- 로그아웃이나 강제 만료가 필요하면 **블랙리스트**(Redis 등)를 함께 운영합니다.

---

## 8. 세션 방식과 비교

| 항목 | 세션 | JWT |
|---|---|---|
| 상태 저장 | 서버(Stateful) | 클라이언트(Stateless) |
| 확장성 | 세션 공유 필요 | 쉬움 |
| 강제 로그아웃 | 쉬움 | 어려움 |
| 저장 데이터 | 세션 ID만 | 사용자 정보 포함 |

---

## 💡 면접 예상 질문

1. **JWT의 구조를 설명해 주세요.**
   → Header, Payload, Signature 세 부분으로 되어 있고, Signature로 변조 여부를 검증합니다.
2. **JWT의 Payload는 안전한가요?**
   → Base64URL 인코딩만 되어 있어 누구나 디코딩할 수 있습니다. 민감한 정보는 넣으면 안 됩니다.
3. **Refresh Token을 왜 사용하나요?**
   → Access Token의 수명을 짧게 해서 탈취 피해를 줄이고, 사용자가 다시 로그인하지 않아도 되게 하려는 목적입니다.
4. **JWT 기반에서 로그아웃은 어떻게 구현하나요?**
   → Refresh Token을 삭제하고, 남아 있는 Access Token은 블랙리스트에 등록해 처리합니다.
5. **세션 방식 대신 JWT를 선택하는 이유는 무엇인가요?**
   → 서버가 상태를 저장하지 않아 확장성이 좋고, 분산 환경에서 인증을 다루기 쉽기 때문입니다.
