# 트리로서 UI 이해하기

React로 만든 화면은 겉으로 보기에는 평평한 페이지처럼 보이지만, 내부에서는 컴포넌트가 서로를 포함하는 계층 구조로 이루어져 있습니다. 이 구조를 트리로 그려 보면 데이터가 어디서 어디로 흐르는지, 어떤 부분이 다시 그려지는지, 코드를 어떻게 나눌지를 훨씬 쉽게 판단할 수 있습니다. 이 글에서는 UI를 트리로 보는 관점을 두 가지 트리인 **렌더 트리**와 **모듈 의존성 트리**를 중심으로 살펴보겠습니다.

## 1. UI는 트리 구조다

다음과 같은 간단한 페이지를 생각해 봅시다.

```jsx
function App() {
  return (
    <div>
      <Header />
      <main>
        <Article />
        <Sidebar />
      </main>
    </div>
  );
}
```

`App`은 `Header`, `Article`, `Sidebar`를 렌더링하고, `Article`과 `Sidebar`는 또 다른 컴포넌트를 렌더링할 수 있습니다. 이렇게 "누가 누구를 렌더링하는가"라는 관계를 따라가면 자연스럽게 나무 모양이 됩니다.

```
App
├── Header
└── Article
    ├── Title
    └── Body
```

나무에는 뿌리가 있고, 가지가 갈라지며, 잎에 해당하는 노드가 있습니다. React의 컴포넌트 트리도 같은 방식으로 이해하면 됩니다. 가장 위에 있는 컴포넌트를 **루트(root)** 라고 부르며, 보통 `App`이 여기에 해당합니다.

## 2. 렌더 트리

**렌더 트리(render tree)** 는 한 번의 렌더링에서 컴포넌트가 만들어 내는 부모-자식 관계를 나타냅니다. 앞의 예시에서 `App`이 `Header`를 자식으로 가지는 것이 바로 렌더 트리의 한 부분입니다.

### 루트 컴포넌트

루트 컴포넌트는 트리의 시작점입니다. 여기서 정의한 상태나 Context 값은 아래쪽 모든 자식에게 전달될 수 있습니다. 따라서 여러 하위 컴포넌트가 함께 써야 하는 데이터는 가능한 한 공통 조상에 두는 것이 일반적입니다.

### 조건부 렌더링과 트리의 변화

렌더 트리는 고정되어 있지 않습니다. 상태나 props에 따라 어떤 컴포넌트가 렌더링될지 달라지므로, 트리의 모양도 함께 달라집니다.

```jsx
function Page({ isLoggedIn }) {
  return (
    <div>
      {isLoggedIn ? <Dashboard /> : <LoginForm />}
    </div>
  );
}
```

`isLoggedIn`이 `true`이면 트리에는 `Dashboard`가 나타나고, `false`이면 `LoginForm`이 나타납니다. 두 컴포넌트는 같은 위치에 있더라도 트리에서는 서로 다른 노드입니다. 이 점이 중요한 이유는, React가 같은 위치의 컴포넌트 타입이 바뀌면 이전 노드의 상태를 버리고 새로 만들기 때문입니다. 즉, 트리의 구조가 바뀌면 그 아래 상태도 함께 바뀝니다.

또한 DOM 요소(`div`, `main` 등)는 React 컴포넌트가 아니지만, 설명을 위해 트리에 함께 표시하는 경우가 많습니다. 컴포넌트 트리는 "컴포넌트가 무엇을 렌더링하는가"에 집중하고, DOM 트리는 그 결과로 브라우저에 만들어지는 요소 구조를 나타냅니다.

## 3. 렌더 트리와 리렌더링

렌더 트리를 이해하면 리렌더링이 어떻게 일어나는지도 예측할 수 있습니다. 기본적으로 부모가 다시 렌더링되면 그 아래의 자식들도 함께 다시 렌더링됩니다. 따라서 다음 구조에서는

```
App (상태 변경)
├── Header
└── Article
    └── Body
```

`App`의 상태가 바뀌면 `Header`, `Article`, `Body`가 모두 다시 실행될 수 있습니다. 자식이 props를 전혀 사용하지 않더라도 말입니다. 이를 줄이려면 상태를 필요한 가장 아래쪽 트리 노드로 내리거나, `memo`로 자식의 불필요한 렌더링을 건너뛰게 할 수 있습니다.

```jsx
const Header = memo(function Header() {
  return <header>사이트 제목</header>;
});
```

이처럼 트리 구조를 먼저 파악하면 "상태를 어디에 둘 것인가"와 "어느 부분만 다시 그려지게 할 것인가"를 체계적으로 결정할 수 있습니다.

## 4. 모듈 의존성 트리

트리는 렌더링에서만 나타나는 것이 아닙니다. 파일 단위로 보면 **모듈 의존성 트리(module dependency tree)** 도 존재합니다. 이는 `import`와 `export`로 연결된 파일들의 관계입니다.

```
index.js (진입점, 루트 모듈)
└── App.js
    ├── Header.js
    └── Article.js
        ├── Title.js
        └── formatDate.js
```

진입점 파일이 루트 모듈이 되고, 그 파일이 가져오는 모듈이 자식이 됩니다. 번들러인 Vite나 webpack은 이 트리를 따라가며 필요한 코드를 모아 하나 혹은 여러 개의 번들 파일을 만듭니다.

렌더 트리와 모듈 의존성 트리는 서로 비슷해 보이지만 다른 개념입니다. 렌더 트리는 실행 중에 컴포넌트가 무엇을 그리는지를 나타내고, 모듈 의존성 트리는 코드가 빌드 시점에 어떻게 연결되는지를 나타냅니다. 한 파일에 여러 컴포넌트가 있을 수 있고, 한 컴포넌트가 여러 파일의 도움을 받을 수도 있습니다.

모듈 트리를 보면 다음과 같은 점을 알 수 있습니다.

- 루트 모듈에서 도달할 수 없는 파일은 번들에 포함되지 않습니다.
- 특정 큰 라이브러리를 여러 깊은 가지에서 가져오면 초기 로딩 비용이 커질 수 있습니다.
- 동적 `import()`를 사용하면 트리의 일부를 나중에 불러오도록 나눌 수 있습니다.

```jsx
const Chart = lazy(() => import('./Chart.js'));
```

## 5. 트리를 읽으면 얻는 것

UI를 트리로 보는 습관은 실무에서 다음과 같은 판단을 도와줍니다.

1. **상태 위치 결정**: 두 컴포넌트가 같은 데이터를 필요로 한다면, 둘의 가장 가까운 공통 조상을 찾아 상태를 둡니다.
2. **props 흐름 파악**: 데이터는 트리를 따라 위에서 아래로 전달됩니다. 너무 깊이 전달해야 한다면 Context나 구조 변경을 고려합니다.
3. **리렌더링 범위 예측**: 상태가 변경되는 노드 아래의 서브트리가 다시 렌더링의 대상이 됩니다.
4. **에러와 로딩 경계 설정**: Error Boundary나 Suspense는 특정 서브트리를 감싸서 그 안의 실패나 대기를 격리합니다.
5. **코드 분할**: 모듈 의존성 트리에서 자주 쓰지 않는 가지를 찾아 지연 로딩합니다.

## 정리

- React 앱은 컴포넌트가 다른 컴포넌트를 렌더링하는 **렌더 트리**로 이루어져 있으며, 가장 위의 루트 컴포넌트에서 시작합니다.
- 조건부 렌더링에 따라 트리의 모양이 바뀌고, 그에 따라 상태도 유지되거나 초기화됩니다.
- 부모가 다시 렌더링되면 기본적으로 그 아래 서브트리가 함께 다시 렌더링됩니다.
- 파일의 `import`/`export` 관계는 **모듈 의존성 트리**를 이루며, 번들링과 코드 분할의 기준이 됩니다.

UI를 트리로 바라보면 복잡한 화면도 부모와 자식의 관계로 나누어 생각할 수 있습니다. 문제가 생겼을 때 "이 데이터는 어느 노드에서 와서 어느 노드로 가는가?"를 묻는 것이 디버깅의 출발점이 됩니다.
