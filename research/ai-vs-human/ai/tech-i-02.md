# 클린코드(Clean Code) & 시큐어코딩(Secure Coding)

## 1. 클린코드란?
**클린코드**는 다른 개발자가 쉽게 읽고, 이해하고, 수정할 수 있는 코드를 말합니다. 로버트 C. 마틴(Uncle Bob)의 저서 *Clean Code*로 널리 알려졌습니다. 코드는 작성하는 시간보다 읽는 시간이 훨씬 길기 때문에, 가독성은 곧 유지보수 비용과 직결됩니다.

> 면접 한 줄 답변: "클린코드는 동작하는 코드를 넘어, 팀원이 의도를 빠르게 파악하고 안전하게 변경할 수 있는 코드입니다."

## 2. 클린코드 핵심 원칙

### 2-1. 의미 있는 이름
- 변수·함수·클래스 이름만으로 의도가 드러나야 합니다.
- `d`, `tmp`, `data2` 같은 이름 대신 `elapsedDays`, `userList`처럼 씁니다.
- 불리언은 `isActive`, `hasPermission`처럼 질문형으로 짓습니다.

### 2-2. 함수는 작게, 한 가지 일만
- **단일 책임**: 함수 하나는 한 가지 일만 합니다.
- 인자는 가능한 한 적게(0~2개) 받고, 부수효과(side effect)를 줄입니다.
- 추상화 수준을 한 함수 안에서 섞지 않습니다.

### 2-3. 주석보다 코드로 설명
- 나쁜 코드에 주석을 덧붙이지 말고 코드를 고칩니다.
- "무엇"이 아니라 "왜"를 설명할 때만 주석을 씁니다.
- 낡은 주석은 거짓말이 되므로 주의해야 합니다.

### 2-4. 중복 제거 (DRY)
같은 로직이 반복되면 함수나 모듈로 추출합니다. 단, 우연히 비슷한 코드를 과하게 추상화하는 것도 경계해야 합니다.

### 2-5. 오류 처리
- 오류 코드 반환보다 **예외**를 사용합니다.
- `null` 반환과 전달을 피하고, `Optional`이나 빈 컬렉션을 활용합니다.
- 예외를 삼키는 빈 `catch` 블록은 금지입니다.

## 3. SOLID 원칙 (자주 나오는 질문)
| 원칙 | 의미 |
|---|---|
| **S**RP | 클래스는 변경 이유가 하나여야 함 |
| **O**CP | 확장에는 열려 있고 수정에는 닫혀 있음 |
| **L**SP | 하위 타입은 상위 타입을 대체 가능해야 함 |
| **I**SP | 사용하지 않는 인터페이스에 의존하지 않음 |
| **D**IP | 구체 클래스가 아닌 추상화에 의존함 |

## 4. 시큐어코딩이란?
**시큐어코딩**은 개발 단계에서 보안 취약점을 만들지 않도록 설계하고 구현하는 활동입니다. 배포 후 패치하는 것보다 개발 초기에 막는 편이 비용이 훨씬 적게 듭니다(Shift-Left). 참고 기준으로는 **OWASP Top 10**, 행정안전부 소프트웨어 개발보안 가이드, CWE가 있습니다.

## 5. 주요 취약점과 대응

### 5-1. SQL 인젝션
- 원인: 사용자 입력을 문자열로 이어 붙여 쿼리를 만드는 것.
- 대응: **PreparedStatement(파라미터 바인딩)**, ORM 사용, 입력값 검증.

```java
// 위험
String sql = "SELECT * FROM users WHERE id = '" + id + "'";
// 안전
PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE id = ?");
ps.setString(1, id);
```

### 5-2. XSS (크로스 사이트 스크립팅)
- 원인: 입력값이 검증 없이 HTML에 출력되는 것.
- 대응: **출력 시 이스케이프**, CSP 헤더 적용, `HttpOnly` 쿠키.

### 5-3. CSRF
- 원인: 사용자가 의도하지 않은 요청이 인증 상태로 전송되는 것.
- 대응: **CSRF 토큰**, `SameSite` 쿠키, 중요 작업 시 재인증.

### 5-4. 인증·인가 결함
- 비밀번호는 **bcrypt, Argon2** 등으로 솔트와 함께 해시하여 저장합니다.
- 권한 검사는 반드시 **서버**에서 수행합니다(IDOR 방지).
- 세션은 로그인 후 재발급하고, 만료 시간을 설정합니다.

### 5-5. 민감정보 노출
- 비밀키, 패스워드, API 키를 소스코드에 하드코딩하지 않습니다(환경변수나 Secret Manager 사용).
- 전송 구간은 TLS, 저장 시에는 암호화합니다.
- 오류 메시지에 스택 트레이스나 내부 정보를 노출하지 않습니다.

### 5-6. 기타
- **경로 조작(Path Traversal)**: `../` 입력을 차단하고 경로를 정규화합니다.
- **안전하지 않은 역직렬화**: 신뢰할 수 없는 데이터는 역직렬화하지 않습니다.
- **취약한 의존성**: SCA 도구로 라이브러리 취약점을 점검합니다.

## 6. 시큐어코딩 기본 원칙
1. **모든 입력은 신뢰하지 않는다** (화이트리스트 기반 검증)
2. **최소 권한의 원칙**
3. **심층 방어** (여러 계층의 보안 장치)
4. **실패 시 안전하게** (Fail Secure)
5. **보안 설정은 기본값부터 안전하게** (Secure by Default)

## 7. 클린코드와 시큐어코딩의 관계
- 읽기 쉬운 코드는 **리뷰가 쉬워** 보안 결함을 일찍 발견할 수 있습니다.
- 입력 검증과 오류 처리를 일관되게 모아 두면 보안 정책을 한곳에서 관리할 수 있습니다.
- 반대로 복잡하고 중복된 코드는 패치 누락과 취약점의 온상이 됩니다.

## 8. 실무 적용 방법
- **코드 리뷰**와 체크리스트 운영
- **정적 분석(SAST)**: SonarQube, SpotBugs 등
- **동적 분석(DAST)**과 **SCA**(의존성 점검)
- 린터·포매터로 스타일 자동화
- 단위 테스트로 리팩터링 안전망 확보

## 9. 예상 면접 질문
1. 클린코드를 위해 평소 어떤 습관을 갖고 있나요?
2. 함수는 얼마나 작아야 한다고 생각하나요?
3. SQL 인젝션이 발생하는 원리와 방어법은 무엇인가요?
4. XSS와 CSRF의 차이를 설명해 보세요.
5. 비밀번호는 어떻게 저장해야 하나요? 암호화와 해시의 차이는 무엇인가요?
6. 보안과 개발 생산성이 충돌할 때 어떻게 판단하나요?

## 10. 마무리 요약
- 클린코드 = **읽기 쉽고 바꾸기 쉬운 코드** (이름, 작은 함수, 중복 제거, SOLID)
- 시큐어코딩 = **취약점을 만들지 않는 코드** (입력 검증, 출력 인코딩, 최소 권한, 안전한 저장)
- 두 가지 모두 결국 **코드 품질과 신뢰성**을 높이는 같은 방향의 활동입니다.
