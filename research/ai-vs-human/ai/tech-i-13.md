# Git Flow vs GitHub Flow vs GitLab Flow

## 1. 개요

브랜치 전략은 여러 개발자가 하나의 저장소에서 충돌 없이 협업하고, 안정적으로 배포하기 위한 **브랜치 생성·병합 규칙**입니다. 대표적인 전략은 다음 세 가지입니다.

- **Git Flow**: 2010년 Vincent Driessen이 제안했습니다. 정해진 주기로 버전을 출시하는 제품에 맞습니다.
- **GitHub Flow**: GitHub이 사용하는 단순한 전략입니다. 지속적 배포(CD)를 전제로 합니다.
- **GitLab Flow**: 두 전략의 중간 형태입니다. 배포 환경별 브랜치를 함께 운영합니다.

> 면접 포인트: "어떤 전략이 가장 좋은가?"에는 정답이 없습니다. **배포 주기, 팀 규모, 운영 환경**에 따라 고른다는 점을 꼭 말하는 것이 좋습니다.

---

## 2. Git Flow

### 브랜치 구성
| 브랜치 | 역할 |
|---|---|
| `main`(master) | 실제 출시된 버전만 보관하며, 태그로 버전을 관리 |
| `develop` | 다음 출시를 위한 통합 브랜치 |
| `feature/*` | 기능 개발용, develop에서 분기해 develop으로 병합 |
| `release/*` | 출시 준비(QA, 버그 수정), develop에서 분기해 main과 develop에 병합 |
| `hotfix/*` | 운영 중 긴급 수정, main에서 분기해 main과 develop에 병합 |

### 장점
- 역할이 명확해서 **여러 버전을 동시에 유지보수**하기 쉽습니다.
- QA 기간을 따로 확보할 수 있어 출시 품질을 관리하기 좋습니다.

### 단점
- 브랜치가 많아 구조가 복잡하고, 병합 충돌과 관리 비용이 커집니다.
- 하루에도 여러 번 배포하는 웹 서비스에는 지나치게 무겁습니다.

### 적합한 경우
모바일 앱, 패키지 소프트웨어, 라이브러리처럼 **버전 단위로 출시**하는 제품.

---

## 3. GitHub Flow

### 흐름
1. `main`은 **항상 배포 가능한 상태**로 유지합니다.
2. 작업할 때마다 `main`에서 이름이 분명한 브랜치를 만듭니다. (예: `fix-login-error`)
3. 커밋한 뒤 원격에 push하고 **Pull Request**를 엽니다.
4. 코드 리뷰와 CI 테스트를 통과하면 `main`에 병합합니다.
5. 병합 직후 곧바로 배포합니다.

### 장점
- 구조가 단순해 배우기 쉽고, 빠른 피드백과 잦은 배포에 유리합니다.
- PR 중심이라 코드 리뷰 문화가 자연스럽게 자리 잡습니다.

### 단점
- 출시 버전 관리나 스테이징·운영 같은 **환경 분리를 표현하기 어렵습니다.**
- 자동화된 테스트와 CI/CD가 갖춰지지 않으면 `main`이 쉽게 불안정해집니다.

### 적합한 경우
SaaS나 웹 서비스처럼 **지속적으로 배포**하는 소규모~중규모 팀.

---

## 4. GitLab Flow

GitHub Flow의 단순함은 유지하면서 **배포 환경과 출시 관리**를 보완한 전략입니다.

### 방식 1: 환경 브랜치(Environment Branch)
```
feature → main → pre-production → production
```
- `main`에서 개발한 코드를 환경 브랜치로 **한 방향(upstream first)으로만** 내려보냅니다.
- 운영 반영 시점을 통제할 수 있습니다. (예: 앱스토어 심사나 정해진 배포 시간)

### 방식 2: 릴리스 브랜치(Release Branch)
- `2-3-stable`, `2-4-stable`처럼 외부에 출시하는 버전마다 브랜치를 둡니다.
- 버그는 **main에 먼저 고친 뒤 cherry-pick**으로 릴리스 브랜치에 반영합니다.

### 장점
- 환경별 배포 상태를 브랜치만 보고 바로 알 수 있습니다.
- Git Flow보다 단순하고, GitHub Flow보다 운영 통제력이 높습니다.

### 단점
- 환경 브랜치가 늘어나면 브랜치마다 상태가 어긋나기 쉽습니다.
- "upstream first" 원칙을 지키지 않으면 수정 사항이 누락될 수 있습니다.

---

## 5. 한눈에 비교

| 항목 | Git Flow | GitHub Flow | GitLab Flow |
|---|---|---|---|
| 복잡도 | 높음 | 낮음 | 중간 |
| 핵심 브랜치 | main, develop | main | main + 환경/릴리스 |
| 배포 주기 | 정기 출시 | 상시 배포 | 상시 + 통제된 배포 |
| 버전 관리 | 강함 | 약함 | 중간~강함 |
| CI/CD 의존도 | 중간 | 매우 높음 | 높음 |
| 대표 사례 | 모바일 앱, 설치형 SW | 웹 서비스, 스타트업 | 다중 환경 운영 조직 |

## 6. 면접 예상 질문과 답변 요령

**Q1. Git Flow에서 hotfix를 main과 develop 양쪽에 병합하는 이유는?**
→ main에만 반영하면 다음 출시 때 develop의 코드가 main을 덮어써서 **같은 버그가 다시 생기기** 때문입니다.

**Q2. GitHub Flow에서 main 안정성은 어떻게 보장하나요?**
→ 브랜치 보호 규칙, 필수 코드 리뷰, CI 자동 테스트, Feature Flag를 함께 써서 보장합니다. 문제가 생기면 빠르게 롤백합니다.

**Q3. 트렁크 기반 개발(Trunk-Based Development)과 비교하면?**
→ GitHub Flow와 비슷하지만 브랜치 수명이 **하루 이내로 더 짧습니다.** 미완성 기능은 Feature Flag로 숨기고, 대규모 조직의 CI/CD에서 많이 씁니다.

**Q4. 우리 팀에 맞는 전략은 어떻게 고르나요?**
→ 다음 순서로 판단합니다.
① 배포가 하루 여러 번인지, 정기 출시인지
② 여러 버전을 동시에 지원해야 하는지
③ 스테이징 같은 중간 환경이 필요한지
④ 자동화 수준이 어느 정도인지

---

## 7. 핵심 요약

- **Git Flow**: 체계적이지만 무겁습니다. 버전 출시형 제품에 맞습니다.
- **GitHub Flow**: 단순하고 빠릅니다. CI/CD가 갖춰진 상시 배포 환경에 맞습니다.
- **GitLab Flow**: 단순함과 통제력을 절충했습니다. 환경별 배포 관리가 필요할 때 씁니다.
- 결론: 전략 자체보다 **팀의 배포 방식과 자동화 수준에 맞추는 것**이 중요합니다.
