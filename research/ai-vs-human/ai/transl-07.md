# HTTP의 진화

**HTTP**(HyperText Transfer Protocol)는 1989년 팀 버너스리가 CERN에서 월드 와이드 웹을 설계하면서 함께 고안한 프로토콜입니다. 처음에는 HTML 문서 한 장을 가져오는 단순한 규약이었지만, 30여 년 동안 웹의 요구가 커지면서 이미지, 스크립트, 영상, API 호출까지 모두 다루는 범용 애플리케이션 프로토콜로 발전했습니다. 이 문서는 HTTP가 어떤 단계를 거쳐 현재의 모습이 되었는지, 각 버전이 어떤 문제를 풀기 위해 등장했는지 살펴봅니다.

## 웹의 탄생과 HTTP/0.9

초기 HTTP는 이름조차 없었고, 나중에 구분을 위해 **HTTP/0.9**라고 부르게 되었습니다. 이 버전은 극도로 단순했습니다.

- 메서드는 `GET` 하나뿐이었습니다.
- 요청은 한 줄로 끝났습니다.
- 응답에는 헤더가 없었고 HTML 파일 내용만 돌아왔습니다.
- 상태 코드가 없어서 오류는 HTML 문서 안에 설명을 담아 보내는 방식으로 처리했습니다.

```http
GET /mypage.html
```

```html
<html>
  이 페이지는 아주 간단합니다.
</html>
```

요청 한 번에 응답 한 번, 그리고 연결을 닫는 구조였기 때문에 구현은 쉬웠지만 HTML 이외의 콘텐츠를 보낼 방법이 없었습니다.

## HTTP/1.0: 확장성의 토대 (1996)

1990년대 중반 브라우저와 서버가 빠르게 늘면서 프로토콜을 확장할 필요가 생겼습니다. 1996년 RFC 1945로 문서화된 **HTTP/1.0**은 다음 요소를 추가했습니다.

- **버전 정보**가 요청 줄에 포함되었습니다.
- **상태 코드**가 응답 첫 줄에 추가되어 요청의 성공과 실패를 알 수 있게 되었습니다.
- **HTTP 헤더**가 요청과 응답 모두에 도입되어 메타데이터를 주고받을 수 있게 되었습니다.
- `Content-Type` 헤더 덕분에 HTML 외에 이미지, 텍스트 등 다양한 문서를 전송할 수 있었습니다.
- `POST`, `HEAD` 같은 메서드가 추가되었습니다.

```http
GET /mypage.html HTTP/1.0
User-Agent: NCSA_Mosaic/2.0 (Windows 3.1)

200 OK
Date: Tue, 15 Nov 1994 08:12:31 GMT
Content-Type: text/html

<HTML>
  ...
</HTML>
```

다만 이 시기에는 표준이 하나로 정리되지 않아 구현마다 동작이 달랐고, 요청마다 새 TCP 연결을 맺어야 하는 비효율이 있었습니다.

## HTTP/1.1: 표준 프로토콜 (1997~)

**HTTP/1.1**은 1997년 RFC 2068로 처음 발표되었고, 이후 RFC 2616(1999)을 거쳐 2014년 RFC 7230~7235로, 다시 2022년 RFC 9110~9112로 정리되었습니다. 20년 넘게 웹의 주력 프로토콜이었던 이유는 실용적인 개선이 한꺼번에 들어갔기 때문입니다.

- **지속 연결(keep-alive)**: 한 TCP 연결을 재사용해 연결 수립 비용을 줄입니다.
- **파이프라이닝**: 응답을 기다리지 않고 요청을 연달아 보낼 수 있게 했습니다. 다만 응답은 요청 순서대로 와야 하므로 실제로는 거의 사용되지 않았습니다.
- **청크 전송 인코딩**: 전체 길이를 미리 모르는 응답도 조각으로 나눠 보낼 수 있습니다.
- **캐시 제어 확장**: `Cache-Control`, `ETag` 등으로 캐시를 정교하게 제어합니다.
- **콘텐츠 협상**: 언어, 인코딩, 형식을 클라이언트와 서버가 합의합니다.
- **`Host` 헤더**: 하나의 IP 주소에서 여러 도메인을 서비스하는 가상 호스팅이 가능해졌습니다.

```http
GET /ko/docs/Web HTTP/1.1
Host: developer.mozilla.org
Accept-Language: ko
```

HTTP/1.1 시대에 웹은 크게 변했습니다. 2000년대에는 **HTTPS**(TLS 위의 HTTP)가 전자상거래와 로그인에 널리 쓰이기 시작했고, `XMLHttpRequest`와 이후 `fetch()`로 페이지 전체를 새로 고치지 않고도 서버와 통신하는 웹 애플리케이션이 등장했습니다. 이 과정에서 `PUT`, `DELETE`, `PATCH` 같은 메서드가 REST API에 활발히 쓰였습니다.

### HTTP/1.1의 한계

페이지 하나가 수십~수백 개의 리소스를 요구하게 되면서 한계가 드러났습니다.

- **헤더 중복**: 매 요청마다 `Cookie`, `User-Agent` 같은 비슷한 헤더가 텍스트로 반복 전송됩니다.
- **회선 선두 차단(HOL blocking)**: 한 연결에서는 앞선 응답이 늦어지면 뒤의 응답도 기다려야 합니다.
- **다중 연결 우회책**: 브라우저가 도메인당 여섯 개 안팎의 연결을 열고, 도메인 샤딩, 스프라이트 이미지, 파일 합치기 같은 최적화 기법이 널리 쓰였습니다.

## HTTP/2: 바이너리와 다중화 (2015)

구글이 실험한 SPDY 프로토콜을 바탕으로 2015년 RFC 7540으로 표준화된 **HTTP/2**는 의미 체계(메서드, 상태 코드, 헤더)는 그대로 두고 **전송 방식**만 바꿨습니다.

- **바이너리 프레이밍**: 텍스트 대신 바이너리 프레임으로 메시지를 나눠 파싱이 효율적이고 오류가 적습니다.
- **다중화(multiplexing)**: 하나의 연결에서 여러 요청과 응답을 동시에 주고받아, HTTP 계층의 회선 선두 차단을 없앱니다.
- **헤더 압축(HPACK)**: 반복되는 헤더를 압축해 오버헤드를 줄입니다.
- **서버 푸시**: 서버가 요청 전에 리소스를 먼저 보낼 수 있었으나, 활용이 어려워 대부분의 브라우저에서 제거되었습니다.
- **스트림 우선순위**: 중요한 리소스를 먼저 받도록 요청할 수 있습니다.

HTTP/2는 사실상 TLS와 함께 쓰이며, 개발자가 애플리케이션 코드를 바꾸지 않아도 서버와 브라우저가 지원하면 속도 향상을 얻는다는 점이 큰 장점이었습니다. 반대로 HTTP/1.1용 최적화 기법은 오히려 불필요해졌습니다.

그러나 HTTP/2도 TCP 위에서 동작하므로 패킷이 하나 손실되면 같은 연결의 모든 스트림이 재전송을 기다리는 **TCP 계층의 회선 선두 차단**은 피할 수 없었습니다.

## HTTP/3: QUIC 위의 HTTP (2022)

**HTTP/3**(RFC 9114, 2022)는 TCP 대신 UDP 기반의 전송 프로토콜 **QUIC**을 사용합니다. 이를 통해 다음과 같은 이점을 얻습니다.

- 스트림이 서로 독립적이어서 한 스트림의 패킷 손실이 다른 스트림을 막지 않습니다.
- TLS 1.3이 QUIC에 통합되어 연결 수립이 빠르고, 재연결 시 0-RTT도 가능합니다.
- **연결 마이그레이션**: IP 주소가 바뀌어도(예: Wi-Fi에서 모바일 망으로 전환) 연결 ID로 세션을 유지합니다.
- 헤더 압축은 QPACK을 사용합니다.

서버는 `Alt-Svc` 헤더나 DNS의 HTTPS 레코드로 HTTP/3 지원을 알리고, 브라우저는 이를 보고 전환합니다.

```http
Alt-Svc: h3=":443"; ma=86400
```

## 버전별 비교

| 버전 | 연도 | 전송 계층 | 형식 | 핵심 특징 |
| --- | --- | --- | --- | --- |
| HTTP/0.9 | 1991 | TCP | 텍스트 | `GET`만 지원, 헤더 없음 |
| HTTP/1.0 | 1996 | TCP | 텍스트 | 헤더, 상태 코드, 콘텐츠 타입 |
| HTTP/1.1 | 1997 | TCP | 텍스트 | 지속 연결, `Host`, 캐시, 청크 전송 |
| HTTP/2 | 2015 | TCP(+TLS) | 바이너리 | 다중화, HPACK 헤더 압축 |
| HTTP/3 | 2022 | QUIC(UDP) | 바이너리 | 독립 스트림, 빠른 연결, 마이그레이션 |

## 변하지 않는 것들

버전이 바뀌어도 HTTP의 **핵심 의미 체계**는 유지됩니다. 메서드, 상태 코드, 헤더 필드, URL, 요청과 응답이라는 모델은 모든 버전에서 같습니다. 그래서 개발자는 `fetch()` 호출이나 서버 로직을 거의 바꾸지 않고도 하위 계층의 개선 효과를 누릴 수 있습니다. 이런 설계는 HTTP가 **확장 가능한 헤더**와 **상태 없는(stateless) 요청** 위에 만들어졌기에 가능했습니다.

또한 새 버전이 나와도 이전 버전이 사라지지 않습니다. 클라이언트와 서버는 TLS의 ALPN 확장 등으로 서로 지원하는 최상위 버전을 협상하고, 지원하지 않으면 낮은 버전으로 되돌아갑니다.

## 정리

HTTP의 진화는 한 줄짜리 문서 요청에서 출발해, 의미 체계는 유지하면서 전송 효율을 높이는 방향으로 이어져 왔습니다. HTTP/1.0과 1.1은 기능과 표준을, HTTP/2는 하나의 연결을 효율적으로 쓰는 방법을, HTTP/3는 TCP의 구조적 한계를 넘는 길을 제시했습니다. 앞으로도 웹의 요구가 변하면 프로토콜은 계속 확장될 것입니다.
