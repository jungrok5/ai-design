# B Tree & B+ Tree

## 1. 개요
B-Tree는 디스크 기반 데이터베이스와 파일 시스템에서 쓰는 **균형 다진 탐색 트리(balanced m-way search tree)**다. 디스크 I/O는 메모리 접근보다 훨씬 비싸므로, 노드 하나에 많은 키를 담아 트리 높이를 낮추는 것이 핵심이다. 노드 하나는 보통 디스크 페이지(블록) 하나에 대응한다.

## 2. B-Tree의 특징
- 모든 리프 노드는 **같은 깊이**에 있다.
- 차수(order)가 m이면 내부 노드는 최대 m개의 자식을 가진다.
- 키와 데이터(레코드 포인터)가 **모든 노드**에 저장된다.
- 삽입 시 노드가 넘치면 **분할(split)**, 삭제 시 키가 부족하면 **병합(merge)** 또는 **재분배(redistribution)**를 수행한다.

## 3. B+ Tree의 특징
B+ Tree는 B-Tree를 변형한 구조로, MySQL InnoDB나 PostgreSQL 인덱스 등 실제 DBMS에서 주로 쓰인다.
- **데이터는 리프 노드에만** 저장되고, 내부 노드는 탐색용 키만 가진다.
- 리프 노드들은 **연결 리스트(linked list)**로 이어져 있어 범위 검색(range query)에 유리하다.
- 내부 노드에 데이터가 없으므로 한 노드에 키를 더 많이 담아 팬아웃이 커지고, 트리가 더 얕아진다.
- 리프의 키 일부가 내부 노드에 중복 저장될 수 있다.

## 4. 비교

| 구분 | B-Tree | B+ Tree |
|---|---|---|
| 데이터 위치 | 모든 노드 | 리프 노드만 |
| 범위 검색 | 트리 순회 필요 | 리프 체인으로 순차 탐색 |
| 노드당 키 수 | 상대적으로 적음 | 많음 (팬아웃 큼) |
| 전체 순회 | 비효율적 | 리프만 훑으면 됨 |
| 주 사용처 | 일부 파일 시스템 | 대부분의 RDBMS 인덱스 |

## 5. 면접 핵심 포인트
- **왜 이진 트리가 아닌가?** 이진 트리는 높이가 log₂N이라 디스크 접근 횟수가 많다. B-Tree는 차수를 키워 높이를 줄이고 I/O를 최소화한다.
- **시간 복잡도**: 탐색·삽입·삭제 모두 평균·최악 O(log_m N)이다.
- **B+ Tree가 인덱스에 적합한 이유**: 팬아웃이 커 높이가 낮고, 리프 체인으로 정렬된 범위 조회를 빠르게 처리한다.
- **클러스터드 인덱스**: InnoDB의 기본키 클러스터드 인덱스는 B+ Tree 리프에 실제 행 데이터가 들어 있다. 보조 인덱스의 리프에는 기본키 값이 저장된다.

## 6. 노드 분할 예시
차수 m=3이면 노드는 최대 2개의 키를 가진다. 키 10, 20, 30을 순서대로 넣으면 세 번째 삽입에서 노드가 넘치고, 가운데 키 20이 부모로 올라가 `[20]`을 루트로 하는 두 자식 `[10]`, `[30]`이 생긴다. 이처럼 분할은 루트까지 전파될 수 있으며, 그때 트리 높이가 1 증가한다.
