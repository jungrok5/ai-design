# 저장 프로시저(Stored PROCEDURE)

## 1. 정의
저장 프로시저는 SQL 문들을 하나의 이름 있는 단위로 묶어 **DB 서버에 미리 컴파일해 저장**해 두고, 이름과 파라미터로 호출해 실행하는 데이터베이스 객체입니다. 변수, 조건문, 반복문, 예외 처리 같은 절차적 로직을 포함할 수 있습니다(Oracle의 PL/SQL, MySQL의 SQL/PSM, SQL Server의 T-SQL).

```sql
CREATE PROCEDURE transfer(IN from_id INT, IN to_id INT, IN amt DECIMAL(10,2))
BEGIN
  START TRANSACTION;
  UPDATE account SET balance = balance - amt WHERE id = from_id;
  UPDATE account SET balance = balance + amt WHERE id = to_id;
  COMMIT;
END;

CALL transfer(1, 2, 5000);
```

## 2. 장점
- **네트워크 비용 절감**: 여러 쿼리를 한 번의 호출로 처리해 왕복 횟수가 줄어듭니다.
- **성능**: 실행 계획이 캐시되어 재사용되므로 파싱·최적화 비용이 감소합니다.
- **보안**: 테이블 직접 접근 권한 없이 프로시저 실행 권한만 부여할 수 있습니다. 파라미터 바인딩으로 SQL 인젝션도 방어하기 쉽습니다.
- **재사용성과 일관성**: 업무 규칙을 한 곳에 두어 여러 애플리케이션이 같은 로직을 공유합니다.
- **트랜잭션 원자성**: 복잡한 다단계 작업을 DB 안에서 한 단위로 보장합니다.

## 3. 단점
- **이식성 저하**: DB 벤더마다 문법이 달라 이전이 어렵습니다(벤더 종속).
- **유지보수·버전 관리의 어려움**: 코드가 DB에 있어 Git 관리, 테스트, 디버깅, CI/CD 적용이 불편합니다.
- **확장성 한계**: 로직이 DB에 몰리면 CPU 부하가 DB로 집중됩니다. DB는 수평 확장이 어려워 병목이 됩니다.
- **비즈니스 로직 분산**: 로직이 애플리케이션과 DB로 나뉘어 파악이 어려워집니다.

## 4. 함수(Function)·트리거와의 비교
| 구분 | 프로시저 | 함수 | 트리거 |
|---|---|---|---|
| 반환값 | 필수 아님(OUT 파라미터 가능) | 반드시 반환 | 없음 |
| 호출 | `CALL`/`EXEC` | SELECT 안에서 사용 가능 | 이벤트 시 자동 실행 |
| 트랜잭션 제어 | 가능 | 제한적 | 제한적 |

## 5. 면접 예상 질문
1. **프로시저를 쓰면 왜 빠른가?** 실행 계획 재사용과 네트워크 왕복 감소 때문입니다. 다만 최신 DB는 일반 쿼리의 계획도 캐싱하므로 차이는 줄었습니다.
2. **요즘은 왜 덜 쓰는가?** 마이크로서비스, ORM, 테스트 자동화, 무중단 배포 흐름과 맞지 않고 DB 확장 부담이 크기 때문입니다.
3. **언제 쓰면 좋은가?** 대량 배치 처리, 데이터 집계, 다단계 트랜잭션처럼 데이터 이동량이 많은 작업에 적합합니다.
4. **SQL 인젝션에 안전한가?** 파라미터를 쓰면 안전하지만, 프로시저 내부에서 동적 SQL(`EXEC(문자열)`)을 문자열 결합으로 만들면 여전히 위험합니다.

## 6. 핵심 요약
저장 프로시저는 **성능과 보안, 트랜잭션 일관성**에 강점이 있지만 **이식성, 버전 관리, 확장성**에서 약점이 있습니다. 면접에서는 장단점을 나열하는 데서 끝내지 말고, 어떤 상황에서 선택하고 어떤 상황에서 피할지 기준을 설명하는 것이 좋습니다.
