React Labs는 활발히 진행 중인 연구 프로젝트에 대한 소식을 전하는 글입니다. 지난 [React 18 출시](/blog/2022/03/29/react-v18) 이후 우리가 어떤 작업을 해왔는지, 그리고 앞으로 무엇을 계획하고 있는지 공유합니다.

## 서버 컴포넌트 {/*server-components*/}

서버 컴포넌트(Server Components)는 2020년 12월에 처음 [소개](/blog/2020/12/21/data-fetching-with-react-server-components)한 이후 꾸준히 개선해 온 기능입니다. 서버 컴포넌트는 클라이언트 앱의 상호작용성과 전통적인 서버 렌더링의 성능을 하나로 결합하는 것을 목표로 합니다. 컴포넌트를 서버에서만 실행하면, 그 컴포넌트의 코드는 번들에 포함되지 않으므로 클라이언트로 전송되는 JavaScript 양이 줄어듭니다.

지난 몇 달간 우리는 다음 작업에 집중했습니다.

- **번들러 통합:** 서버 컴포넌트가 실제 프레임워크에서 동작하려면 번들러와의 긴밀한 협업이 필요합니다. Webpack과 Vite 등 주요 번들러가 서버 컴포넌트의 경계를 이해할 수 있도록 API를 다듬고 있습니다.
- **모듈 경계 지정:** 파일 상단에 `'use client'` 지시어를 사용해 서버와 클라이언트 모듈의 경계를 표시하는 방식을 구체화했습니다.
- **비동기 컴포넌트:** 서버 컴포넌트에서는 `async/await`를 사용해 데이터를 직접 읽을 수 있도록 하는 방향을 탐색하고 있습니다.

```js
// 서버 컴포넌트 예시
async function Note({ id }) {
  const note = await db.notes.get(id);
  return <article>{note.body}</article>;
}
```

서버 컴포넌트는 아직 안정화되지 않았으며, 당분간은 프레임워크 개발자를 위한 기반 기능으로 제공될 예정입니다. 일반적인 앱 개발자는 Next.js와 같은 프레임워크를 통해 자연스럽게 이 기능을 접하게 될 것입니다.

## 에셋 로딩 {/*asset-loading*/}

현재 스크립트, 외부 스타일, 폰트, 이미지 같은 에셋(asset)을 불러오는 방식은 대부분 React 바깥에서 처리됩니다. 이로 인해 서버 렌더링, 스트리밍, 서버 컴포넌트, Suspense와 조화롭게 동작시키기가 쉽지 않습니다.

우리는 다음과 같은 목표로 에셋 로딩 API를 연구하고 있습니다.

1. 컴포넌트가 렌더링되는 시점에 필요한 에셋을 함께 선언할 수 있게 한다.
2. 에셋이 로드되기 전에는 화면을 노출하지 않도록 Suspense와 통합한다.
3. 같은 에셋이 여러 컴포넌트에서 요청되어도 중복 로딩하지 않는다.
4. 서버 렌더링 중에는 에셋의 우선순위를 고려해 스트리밍 순서를 결정한다.

이 작업이 완료되면 스타일시트가 늦게 도착해 화면이 깜빡이거나 레이아웃이 흔들리는 문제를 줄일 수 있을 것으로 기대합니다.

## 정적 서버 렌더링 최적화 {/*static-server-rendering-optimizations*/}

정적 사이트 생성(SSG)과 증분 정적 재생성(ISR)은 캐시할 수 있는 페이지를 미리 만들어 두는 훌륭한 방법입니다. 하지만 React의 서버 렌더링은 본래 요청마다 동적으로 실행되는 환경을 전제로 설계되었기 때문에, 정적 콘텐츠에 특화된 최적화 여지가 남아 있습니다.

우리는 정적 렌더링을 위한 새로운 서버 API를 탐색하고 있습니다. 예를 들어 모든 데이터가 준비될 때까지 기다린 뒤 완성된 HTML을 한 번에 만들어 내는 방식입니다. 이 경우 스트리밍에 필요한 부가 기능을 생략할 수 있어 더 단순하고 빠른 렌더링이 가능합니다.

## 서버 렌더링을 위한 React 최적화 컴파일러 {/*react-optimizing-compiler*/}

React는 상태가 바뀌면 영향을 받는 컴포넌트를 다시 렌더링하는 방식으로 UI를 갱신합니다. 이 모델은 단순하고 예측 가능하지만, 불필요한 재렌더링을 피하려면 개발자가 `useMemo`, `useCallback`, `memo`로 직접 메모이제이션을 해야 하는 경우가 많습니다.

우리는 이 수동 작업을 자동화하는 **최적화 컴파일러**를 연구하고 있습니다. 컴파일러는 코드를 정적으로 분석해 어떤 값이 언제 바뀌는지 파악하고, 필요한 부분만 다시 계산하도록 코드를 변환합니다. 핵심 원칙은 다음과 같습니다.

- 개발자가 작성한 코드의 **의미는 그대로 유지**한다.
- [React의 규칙](/reference/rules)을 지키는 코드라면 별도의 수정 없이 동작해야 한다.
- 규칙을 위반하는 코드는 안전하게 건너뛰고, 린터가 이를 알려 준다.

현재는 내부 앱에서 실험하며 성능 향상 폭과 안전성을 측정하고 있습니다. 아직 공개 시점을 논의할 단계는 아니지만, 개발자의 부담을 크게 덜어 줄 가능성이 있는 작업입니다.

## 오프스크린 {/*offscreen*/}

오늘날 화면에서 UI를 숨기려면 두 가지 선택지가 있습니다. CSS로 숨기면 컴포넌트의 상태는 유지되지만 숨겨진 상태에서도 계속 렌더링 비용이 듭니다. 반대로 언마운트하면 비용은 사라지지만 스크롤 위치나 입력값 같은 상태가 사라집니다.

**오프스크린(Offscreen)** 은 이 둘의 장점을 결합하려는 시도입니다. 숨겨진 UI의 상태를 보존하면서도, 화면에 보이지 않는 동안에는 우선순위를 낮춰 렌더링하거나 이펙트를 정리합니다. 활용 가능성은 다음과 같습니다.

- 탭 전환이나 뒤로 가기 시 이전 화면을 **즉시 복원**
- 사용자가 곧 이동할 가능성이 높은 화면을 **미리 렌더링**
- 가상 리스트에서 화면 밖 항목의 **상태 유지**

오프스크린 컴포넌트를 안전하게 쓰려면 이펙트가 여러 번 설정되고 정리되어도 문제없이 동작해야 합니다. 그래서 React 18의 Strict Mode에서 도입한 "이펙트 재실행" 검사가 이 기능의 중요한 기반이 됩니다.

## 트레이싱과 전환 추적 {/*transition-tracing*/}

트랜지션(Transition)은 업데이트를 긴급하지 않은 것으로 표시해 사용자 입력을 방해하지 않도록 해 줍니다. 그러나 실제 앱에서는 "이 전환이 실제로 얼마나 걸렸는가?"를 측정하기가 어렵습니다.

우리는 **트랜지션 트레이싱(Transition Tracing)** API를 개발하고 있습니다. 이를 이용하면 특정 전환이 시작되어 완료될 때까지의 시간을 측정하고, Suspense 경계가 어떻게 해제되었는지 추적할 수 있습니다. 느린 상호작용의 원인을 찾아 개선하는 데 도움이 될 것입니다.
