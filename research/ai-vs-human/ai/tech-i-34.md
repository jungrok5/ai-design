# HTTP Request Methods

## 1. 개요
HTTP 메서드는 클라이언트가 서버의 **리소스에 어떤 동작을 요청하는지** 나타냅니다. REST API에서는 URI로 리소스를 가리키고, 메서드로 그 리소스에 할 행위를 표현합니다.

## 2. 주요 메서드

| 메서드 | 용도 | 요청 Body | 안전 | 멱등 |
|---|---|---|---|---|
| GET | 리소스 조회 | 보통 없음 | O | O |
| POST | 리소스 생성, 처리 요청 | 있음 | X | X |
| PUT | 리소스 전체 교체 (없으면 생성) | 있음 | X | O |
| PATCH | 리소스 일부 수정 | 있음 | X | 보장 안 됨 |
| DELETE | 리소스 삭제 | 보통 없음 | X | O |
| HEAD | GET과 같지만 헤더만 받음 | 없음 | O | O |
| OPTIONS | 지원하는 메서드 확인, CORS Preflight | 없음 | O | O |

## 3. 핵심 개념
- **안전(Safe)**: 호출해도 서버의 리소스가 바뀌지 않습니다. 로그가 쌓이는 정도의 부수 효과는 상관없습니다.
- **멱등(Idempotent)**: 같은 요청을 여러 번 보내도 결과(서버 상태)는 한 번 보냈을 때와 같습니다. 그래서 타임아웃이 나면 **자동으로 재시도해도 안전한지** 판단하는 기준이 됩니다.
- **캐시 가능(Cacheable)**: 실무에서는 GET과 HEAD를 주로 캐시합니다.

## 4. 자주 나오는 면접 질문

**Q. PUT과 PATCH의 차이는?**
PUT은 리소스를 **통째로 교체**합니다. 그래서 보내지 않은 필드는 null이 되거나 지워질 수 있습니다. PATCH는 **보낸 필드만 수정**합니다.

**Q. POST와 PUT의 차이는?**
POST는 서버가 리소스 위치(URI)를 정하고, 호출할 때마다 새 리소스가 생길 수 있어 멱등하지 않습니다. PUT은 클라이언트가 URI를 지정하고, 여러 번 호출해도 결과가 같아 멱등합니다.

**Q. GET으로 데이터를 보내면 안 되는 이유는?**
GET은 쿼리 스트링으로 데이터를 보냅니다. 그래서 URL에 데이터가 그대로 드러나고, 브라우저 기록이나 서버 로그에 남으며, 길이 제한도 있습니다. 민감한 정보나 상태를 바꾸는 요청에는 맞지 않습니다.

**Q. DELETE는 왜 멱등한가?**
처음 호출하면 200, 그다음부터는 404가 올 수 있어 **응답 코드는 달라집니다**. 하지만 "리소스가 없다"는 서버 상태는 똑같기 때문에 멱등합니다.

## 5. 정리
- 조회는 GET, 생성은 POST, 전체 교체는 PUT, 부분 수정은 PATCH, 삭제는 DELETE
- 재시도 정책을 설계할 때는 **멱등성**을 기준으로 판단합니다.
- OPTIONS는 CORS Preflight 요청에 쓰인다는 점까지 알아두면 좋습니다.
