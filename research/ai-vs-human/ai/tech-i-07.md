# Object-Oriented Programming

## 1. 개요

**객체지향 프로그래밍(OOP)**은 프로그램을 **객체(Object)**들의 모음으로 보고, 객체들이 메시지를 주고받으며 협력하도록 설계하는 패러다임입니다. 객체는 **상태(데이터, 필드)**와 **행위(메서드)**를 함께 가집니다.

| 구분 | 절차지향 | 객체지향 |
|---|---|---|
| 중심 | 함수와 실행 순서 | 데이터와 행위를 묶은 객체 |
| 장점 | 단순하고 실행 흐름을 따라가기 쉬움 | 재사용성, 확장성, 유지보수성 |
| 단점 | 규모가 커지면 수정 범위가 넓어짐 | 설계가 어렵고 추상화 비용이 생김 |

> 💡 **면접 포인트**: "OOP는 현실을 모델링하는 방식"이라고만 답하면 부족합니다. **"책임을 객체에 나눠 주고, 변경이 생겨도 영향 범위를 줄이기 위한 설계 방법"**이라고 답하면 더 좋습니다.

## 2. OOP의 4대 특성

### ① 캡슐화 (Encapsulation)
- 데이터와 그 데이터를 다루는 메서드를 하나로 묶고, 내부 구현은 **외부에서 숨깁니다(정보 은닉)**.
- 접근 제어자(`private`, `protected`, `public`)로 공개 범위를 정합니다.
- **효과**: 내부 구현을 바꿔도 외부 코드에 영향이 적고, 객체의 상태를 잘못된 값으로 바꾸는 일을 막을 수 있습니다.

```java
public class Account {
    private long balance;

    public void withdraw(long amount) {
        if (amount > balance) throw new IllegalStateException("잔액 부족");
        balance -= amount;
    }
}
```

> ⚠️ getter와 setter를 무조건 만들면 캡슐화가 깨집니다. **"Tell, Don't Ask"** 원칙에 따라 객체에 데이터를 묻지 말고 일을 시켜야 합니다.

### ② 상속 (Inheritance)
- 부모 클래스의 속성과 메서드를 자식 클래스가 물려받습니다.
- **is-a 관계**일 때 사용합니다(예: `Dog is an Animal`).
- **단점**: 부모와 자식이 강하게 결합되고, 부모를 수정하면 자식이 깨질 수 있습니다(취약한 기반 클래스 문제).

### ③ 다형성 (Polymorphism)
- 같은 메시지를 보내도 객체 타입에 따라 서로 다르게 동작합니다.
- **오버라이딩**은 런타임 다형성(동적 바인딩), **오버로딩**은 컴파일 타임 다형성입니다.

```java
Animal a = new Dog();
a.speak();  // 실제 객체인 Dog의 speak() 호출
```

### ④ 추상화 (Abstraction)
- 공통된 핵심 특징만 뽑아내고 불필요한 세부 사항은 감춥니다.
- 추상 클래스나 인터페이스로 **"무엇을 하는가"**만 정의하고, **"어떻게 하는가"**는 구현체에 맡깁니다.

---

## 3. 오버로딩 vs 오버라이딩

| 구분 | 오버로딩 (Overloading) | 오버라이딩 (Overriding) |
|---|---|---|
| 정의 | 같은 이름, 다른 매개변수 | 부모 메서드를 자식이 재정의 |
| 위치 | 같은 클래스 안 | 상속 관계 |
| 결정 시점 | 컴파일 타임 | 런타임 |
| 시그니처 | 매개변수 개수나 타입이 달라야 함 | 메서드 시그니처가 같아야 함 |

---

## 4. 추상 클래스 vs 인터페이스

| 구분 | 추상 클래스 | 인터페이스 |
|---|---|---|
| 목적 | 공통 기능 재사용 (is-a) | 역할과 규약 정의 (can-do) |
| 다중 상속 | 불가 | 다중 구현 가능 |
| 상태(필드) | 인스턴스 필드 가능 | 상수만 가능 |
| 생성자 | 있음 | 없음 |

- Java 8부터 인터페이스에 `default` 메서드와 `static` 메서드를 넣을 수 있습니다.
- **선택 기준**: 공통 구현을 공유해야 하면 추상 클래스, 서로 다른 클래스에 같은 역할을 부여해야 하면 인터페이스를 씁니다.

## 5. SOLID 원칙

| 원칙 | 내용 | 핵심 키워드 |
|---|---|---|
| **S**RP (단일 책임) | 클래스는 하나의 책임만 가져야 함 | 변경할 이유는 하나뿐 |
| **O**CP (개방-폐쇄) | 확장에는 열려 있고 수정에는 닫혀 있음 | 추상화와 다형성 활용 |
| **L**SP (리스코프 치환) | 자식 타입은 부모 타입을 대체할 수 있어야 함 | 정사각형-직사각형 문제 |
| **I**SP (인터페이스 분리) | 클라이언트가 쓰지 않는 메서드에 의존하면 안 됨 | 작은 인터페이스 여러 개 |
| **D**IP (의존 역전) | 구체 클래스가 아니라 추상에 의존해야 함 | DI, 스프링 IoC |

> 💡 **OCP 예시**: 결제 수단을 추가할 때 `if-else`를 고치는 대신 `PaymentStrategy` 인터페이스의 새 구현체만 추가합니다. 전략 패턴이 대표적인 예입니다.

---

## 6. 상속보다 합성 (Composition over Inheritance)

- **상속**은 화이트박스 재사용입니다. 부모의 내부 구현이 자식에게 드러나서 결합도가 높아집니다.
- **합성**은 블랙박스 재사용입니다. 다른 객체를 필드로 가지고 기능을 위임하므로, 런타임에 구현을 바꿀 수 있고 결합도가 낮습니다.
- **기준**: 진짜 is-a 관계이고 LSP를 지킬 수 있을 때만 상속하고, 나머지 경우에는 합성(**has-a**)을 씁니다.

---

## 7. 결합도와 응집도

- **응집도(Cohesion)**: 모듈 안의 요소들이 얼마나 관련되어 있는지를 뜻하며, **높을수록** 좋습니다.
- **결합도(Coupling)**: 모듈 사이의 의존 정도를 뜻하며, **낮을수록** 좋습니다.
- 좋은 OOP 설계의 목표는 **높은 응집도와 낮은 결합도**입니다.

## 8. 예상 면접 질문

1. **OOP의 4대 특성을 설명해 주세요.**
   → 캡슐화, 상속, 다형성, 추상화를 각각 한 문장 정의와 예시로 설명합니다.
2. **다형성이 왜 중요한가요?**
   → 클라이언트 코드를 바꾸지 않고 새 구현을 추가할 수 있기 때문입니다(OCP 실현).
3. **상속의 단점과 대안은 무엇인가요?**
   → 강한 결합과 캡슐화 파괴가 단점이고, 대안은 합성과 위임입니다.
4. **인터페이스와 추상 클래스는 각각 언제 쓰나요?**
   → 역할 규약이 필요하면 인터페이스, 공통 상태와 구현을 재사용하려면 추상 클래스를 씁니다.
5. **DIP와 DI의 차이는 무엇인가요?**
   → DIP는 "추상에 의존하라"는 설계 원칙이고, DI는 의존성을 외부에서 주입하는 구현 기법입니다.
6. **LSP를 위반하는 예를 들어 보세요.**
   → `Square extends Rectangle`에서 `setWidth`를 호출하면 높이까지 바뀌어서 부모의 계약이 깨집니다.

---

### ✅ 한 줄 요약
> OOP는 **책임 있는 객체들이 협력**하도록 설계해 **변경에 유연한 코드**를 만드는 방법입니다. 4대 특성과 SOLID는 이 목표를 이루기 위한 도구입니다.
