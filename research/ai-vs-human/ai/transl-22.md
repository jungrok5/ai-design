# 웹 성능이란

**웹 성능**(Web performance)은 웹 사이트나 애플리케이션이 얼마나 빠르게 로드되고, 사용자의 입력에 얼마나 즉각적으로 반응하며, 사용하는 동안 얼마나 부드럽게 동작하는지를 나타내는 척도입니다. 또한 이러한 속도와 반응성을 개선하기 위한 측정 기법과 최적화 방법을 아우르는 말이기도 합니다.

웹 성능은 단순한 기술적 지표가 아닙니다. 사용자 경험, 접근성, 전환율, 검색 순위, 운영 비용에 이르기까지 웹 서비스의 거의 모든 측면에 영향을 줍니다. 이 문서에서는 웹 성능의 개념, 중요한 이유, 핵심 지표, 그리고 개선을 시작하는 방법을 소개합니다.

## 웹 성능이 중요한 이유

### 사용자 경험과 유지율

사용자는 느린 사이트를 오래 기다려 주지 않습니다. 페이지가 몇 초 안에 표시되지 않으면 많은 사용자가 이탈하고, 한 번 불편을 겪은 사용자는 다시 방문하지 않을 가능성이 높습니다. 반대로 빠르고 매끄러운 사이트는 신뢰감을 주고 사용자가 더 오래 머물도록 만듭니다.

### 접근성과 포용성

모든 사용자가 최신 기기와 빠른 네트워크를 쓰는 것은 아닙니다. 저사양 휴대폰, 불안정한 모바일 연결, 데이터 요금 부담이 있는 환경의 사용자도 많습니다. 성능을 고려한 설계는 이런 사용자를 포함해 더 많은 사람이 서비스를 이용할 수 있게 합니다. 즉, 웹 성능은 곧 접근성의 일부입니다.

### 비즈니스 성과

성능 개선은 전환율, 매출, 페이지 조회 수 같은 비즈니스 지표와 밀접하게 연결됩니다. 로드 시간이 짧아질수록 구매, 가입, 콘텐츠 소비 같은 목표 행동을 완료하는 비율이 올라가는 경향이 있습니다. 검색 엔진도 페이지 경험을 순위 결정 요소의 하나로 고려합니다.

### 자원과 환경

전송하는 데이터가 줄어들면 서버 비용과 네트워크 사용량이 줄고, 사용자 기기의 배터리 소모도 감소합니다. 이는 전체적인 에너지 사용량을 줄이는 데에도 도움이 됩니다.

## 인지된 성능과 실제 성능

웹 성능을 이야기할 때는 **실제 성능**과 **인지된 성능**을 구분하는 것이 유용합니다.

- **실제 성능**: 시간으로 측정할 수 있는 객관적 수치입니다. 예를 들어 첫 바이트가 도착하기까지의 시간이나 모든 리소스가 로드되는 데 걸린 시간이 해당합니다.
- **인지된 성능**: 사용자가 속도를 어떻게 느끼는가에 대한 주관적 경험입니다. 같은 로드 시간이라도 화면에 콘텐츠가 점진적으로 나타나거나 진행 상태가 분명하게 표시되면 더 빠르게 느껴집니다.

따라서 좋은 성능 최적화는 수치를 줄이는 데서 그치지 않고, 사용자가 기다리는 동안 무엇을 보고 느끼는지까지 설계에 포함합니다. 스켈레톤 화면, 점진적 이미지 로딩, 즉각적인 시각적 피드백 등이 대표적인 예입니다.

## 웹 성능의 주요 지표

성능을 개선하려면 먼저 측정해야 합니다. 다음은 널리 사용되는 지표입니다.

| 지표 | 설명 |
| --- | --- |
| TTFB (Time to First Byte) | 요청을 보낸 뒤 응답의 첫 바이트가 도착하기까지의 시간 |
| FCP (First Contentful Paint) | 텍스트나 이미지 등 첫 콘텐츠가 화면에 그려지는 시점 |
| LCP (Largest Contentful Paint) | 뷰포트 안에서 가장 큰 콘텐츠 요소가 렌더링되는 시점 |
| INP (Interaction to Next Paint) | 사용자의 상호작용에 화면이 응답하기까지 걸리는 시간 |
| CLS (Cumulative Layout Shift) | 로딩 중 예상치 못하게 레이아웃이 이동하는 정도 |
| TBT (Total Blocking Time) | 메인 스레드가 차단되어 입력에 응답하지 못한 총 시간 |

이 중 LCP, INP, CLS는 **Core Web Vitals**로 불리며 각각 로딩 속도, 반응성, 시각적 안정성을 대표합니다. 이 세 가지는 사용자 경험의 핵심 측면을 요약하기 때문에 우선적으로 관리할 지표로 널리 권장됩니다.

## 페이지가 표시되기까지의 과정

브라우저가 URL을 받아 화면에 페이지를 그리기까지는 여러 단계를 거칩니다.

1. **탐색(Navigation)**: DNS 조회, TCP 연결, TLS 협상을 거쳐 서버에 연결합니다.
2. **응답**: 서버가 HTML 문서를 보내면 브라우저가 파싱을 시작합니다.
3. **리소스 로딩**: HTML에서 참조하는 CSS, JavaScript, 이미지, 글꼴 등을 요청합니다.
4. **렌더링**: DOM과 CSSOM을 만들고, 레이아웃을 계산한 뒤 화면에 그립니다.
5. **상호작용**: JavaScript가 실행되며 페이지가 사용자 입력에 반응할 준비를 합니다.

각 단계에는 병목이 생길 수 있습니다. 느린 서버 응답, 렌더링을 막는 CSS와 JavaScript, 지나치게 큰 이미지, 메인 스레드를 오래 점유하는 스크립트 등이 대표적입니다. 어느 단계가 문제인지 파악하는 것이 개선의 출발점입니다.

## 성능을 개선하는 일반적인 방법

### 전송량 줄이기

- 이미지를 적절한 크기와 최신 형식(WebP, AVIF 등)으로 제공합니다.
- CSS, JavaScript, HTML을 압축(minify)하고 gzip이나 Brotli로 전송합니다.
- 사용하지 않는 코드를 제거하고 필요한 코드만 불러옵니다(코드 분할, 트리 셰이킹).

### 요청 최적화하기

- HTTP 캐시를 적극적으로 활용하고 CDN으로 콘텐츠를 사용자와 가까운 곳에서 제공합니다.
- 중요한 리소스는 `preload`, 곧 연결할 출처는 `preconnect`로 미리 알려 줍니다.
- 화면 밖 이미지와 iframe은 `loading="lazy"`로 지연 로딩합니다.

### 렌더링 최적화하기

- 렌더링을 막는 CSS와 JavaScript를 줄이거나 `defer`, `async`로 불러옵니다.
- 이미지와 광고 영역에 크기를 미리 지정해 레이아웃 이동을 방지합니다.
- 긴 작업을 나누어 메인 스레드가 오래 차단되지 않도록 합니다.

### 서버와 네트워크 개선하기

- 서버 응답 시간을 줄이고 HTTP/2 이상의 프로토콜을 사용합니다.
- 불필요한 리디렉션을 피합니다.

## 성능 측정 도구

성능 데이터는 두 가지 방식으로 수집할 수 있습니다.

- **실험실 데이터(Lab data)**: 통제된 환경에서 측정합니다. Lighthouse나 브라우저 개발자 도구의 성능 패널이 대표적이며, 문제를 재현하고 원인을 분석하기에 적합합니다.
- **현장 데이터(Field data)**: 실제 사용자의 환경에서 수집합니다. 다양한 기기와 네트워크에서의 실제 경험을 반영하며, Performance API나 RUM(Real User Monitoring) 도구를 통해 얻을 수 있습니다.

두 방식은 서로를 보완합니다. 현장 데이터로 실제 문제를 발견하고, 실험실 데이터로 원인을 찾아 개선한 뒤, 다시 현장 데이터로 효과를 확인하는 순환이 이상적입니다.

## 성능은 지속적인 과정입니다

웹 성능은 한 번 최적화하고 끝나는 일이 아닙니다. 기능이 추가되고 서드파티 스크립트가 늘어나면 성능은 서서히 나빠지기 쉽습니다. 이를 막으려면 개발 초기부터 성능을 고려하고, **성능 예산**(performance budget)을 정해 자원 크기나 지표의 한계를 관리하며, 배포 과정에 자동화된 측정을 포함하는 것이 좋습니다.
