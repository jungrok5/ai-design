## 1. 프레임워크 & 라이브러리

### React 생태계: 서버와 클라이언트의 경계 재정립
React는 서버 컴포넌트, `Suspense`, `use` 훅, Actions를 축으로 데이터 패칭과 폼 처리 방식을 바꾸고 있습니다. 과거에는 `useEffect`로 데이터를 가져오고 로딩 상태를 직접 관리했습니다. 지금은 **서버에서 데이터를 준비하고, 클라이언트에는 꼭 필요한 상호작용만 남기는 구조**가 권장됩니다. 도입 시 먼저 따져볼 점은 세 가지입니다.

1. 정말 클라이언트 상태가 필요한 컴포넌트인지 확인합니다.
2. `"use client"` 경계를 가능한 한 트리의 말단으로 내립니다.
3. 직렬화할 수 없는 값(함수, 클래스 인스턴스)이 경계를 넘지 않는지 점검합니다.

### 메타 프레임워크: 선택지가 넓어졌습니다
Next.js, Remix(React Router), Astro, SvelteKit, Nuxt는 모두 파일 기반 라우팅과 스트리밍 SSR을 지원합니다. 그래서 선택 기준이 기능 유무보다 **팀의 숙련도, 배포 환경, 콘텐츠 중심인지 앱 중심인지**로 옮겨 가고 있습니다. 콘텐츠가 많은 사이트는 Astro의 아일랜드 구조가 유리하고, 복잡한 대시보드는 React 기반 풀스택 프레임워크가 낫습니다.

### 시그널(Signals) 논의 계속
Solid, Svelte(Runes), Vue, Angular가 세밀한 반응성 모델로 수렴하는 모습이 뚜렷합니다. 언어 차원에서 시그널을 표준화하자는 TC39 제안도 논의가 이어지고 있어 지켜볼 만합니다.

## 2. 언어 & 개발 도구

### TypeScript 컴파일러의 네이티브 이전
TypeScript 팀은 컴파일러를 네이티브 코드로 옮기는 작업을 진행해 왔고, 대형 모노레포에서 타입 체크 시간을 크게 줄이는 것이 목표입니다. CI 시간이 길어 고민이라면 다음을 먼저 확인해 보세요.

- `tsconfig`의 `include`/`exclude` 범위가 과도하지 않은지
- `skipLibCheck`와 프로젝트 레퍼런스를 활용하고 있는지
- 타입 체크와 린트를 병렬로 실행하는지

### 번들러와 린터의 Rust·Go화
Vite 진영의 Rolldown과 Oxc, Biome, SWC, esbuild가 빌드와 린트 속도를 끌어올리고 있습니다. 한꺼번에 갈아엎기보다 **린트 → 포매터 → 번들러 순으로 단계적으로 교체**하는 편이 위험이 적습니다.

### 패키지 관리와 런타임
pnpm 워크스페이스, Bun, Deno, Node의 LTS 라인이 각자 영역을 넓히고 있습니다. 런타임을 바꾸기 전에는 네이티브 애드온 호환성과 CI 캐시 전략부터 점검하세요.

## 3. 웹 플랫폼 & CSS

### 라이브러리 없이 가능한 것들
최근 몇 년간 브라우저에 들어온 기능 덕분에 예전에 JS로 구현하던 UI를 CSS로 대체할 수 있습니다.

| 기능 | 용도 |
|---|---|
| Container Queries | 뷰포트가 아닌 부모 크기 기준의 반응형 |
| `:has()` | 부모·형제 상태 기반 스타일링 |
| View Transitions | 페이지·상태 전환 애니메이션 |
| Scroll-driven Animations | 스크롤 연동 효과 |
| Anchor Positioning | 툴팁·팝오버 위치 계산 |
| `popover` / `<dialog>` | 모달·팝오버의 네이티브 구현 |

도입 전에는 [Baseline](https://web.dev/baseline) 상태와 지원 브라우저 범위를 확인하고, `@supports`로 점진적 향상을 적용하세요.

### Temporal API
`Date`의 오랜 문제(시간대, 불변성, 파싱)를 해결할 `Temporal`이 브라우저에 순차적으로 들어오고 있습니다. 날짜 라이브러리 의존을 줄일 기회지만, 당분간은 폴리필과 함께 쓰는 것이 안전합니다.

### Interop 프로젝트
브라우저 벤더들이 해마다 호환성 개선 목표를 공동으로 발표하고 있습니다. 올해 목록은 기능 도입 시점을 가늠하는 좋은 로드맵입니다.

## 4. 성능 & 접근성

### Core Web Vitals는 INP 중심으로
응답성 지표인 **INP(Interaction to Next Paint)**가 FID를 대체한 이후, 긴 작업 분할이 핵심 과제가 됐습니다.

- 긴 이벤트 핸들러는 `scheduler.yield()` 또는 `setTimeout`으로 쪼갭니다.
- 무거운 계산은 Web Worker로 옮깁니다.
- 리스트가 길면 가상화를 적용합니다.
- 측정은 실제 사용자 데이터(RUM)를 우선하고, 랩 데이터는 보조로 씁니다.

### 접근성은 기능입니다
유럽 접근성법(EAA) 시행 이후 접근성이 규정 준수 문제로 다뤄지고 있습니다. 코드 리뷰에서 다음 다섯 가지만 챙겨도 효과가 큽니다.

1. 시맨틱 태그를 쓰고 `div` 버튼을 피합니다.
2. 키보드만으로 모든 흐름이 가능한지 확인합니다.
3. 포커스 표시를 제거하지 않습니다.
4. 색 대비 4.5:1 이상을 지킵니다.
5. 이미지에 의미 있는 `alt`를 제공합니다.

## 5. AI와 프론트엔드 개발

AI 코딩 도구가 컴포넌트 초안, 테스트, 마이그레이션에 널리 쓰이고 있습니다. 쓸 때 지켜야 할 원칙은 세 가지입니다.

- **생성 코드도 리뷰 대상입니다.** 접근성과 보안(XSS, 의존성)을 특히 확인합니다.
- **디자인 토큰과 컴포넌트 규칙을 문서화해 두면** 결과물 품질이 눈에 띄게 좋아집니다.
- **테스트를 먼저 두면** 대규모 자동 수정이 훨씬 안전합니다.
