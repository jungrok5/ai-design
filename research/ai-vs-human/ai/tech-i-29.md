# 캐시 메모리(Cache Memory)

## 1. 개념
캐시는 CPU와 주기억장치(DRAM) 사이의 속도 차이를 줄이기 위해 두는 **작고 빠른 SRAM 기반 메모리**다. 자주 쓰는 데이터를 CPU 가까이에 복사해 두어 평균 접근 시간을 낮춘다. 핵심 전제는 **지역성(Locality)** 이다.

- **시간 지역성**: 한 번 접근한 데이터는 가까운 미래에 다시 접근될 가능성이 높다. (반복문의 루프 변수)
- **공간 지역성**: 접근한 주소의 인접 주소가 곧 접근될 가능성이 높다. (배열 순회)

그래서 캐시는 한 워드가 아니라 **캐시 라인(블록, 보통 64바이트)** 단위로 데이터를 가져온다.

## 2. 메모리 계층 구조
레지스터 → L1 → L2 → L3 → DRAM → SSD/HDD 순으로 갈수록 용량은 커지고 속도는 느려지며 비트당 가격은 낮아진다.

- **L1**: 코어별 전용, 수십 KB, 약 1ns 이내. 보통 명령어(I-Cache)와 데이터(D-Cache)로 분리(하버드 구조).
- **L2**: 코어별 전용 또는 일부 공유, 수백 KB~수 MB.
- **L3**: 전체 코어 공유(LLC), 수 MB~수십 MB.

## 3. 히트와 미스
- **Hit**: 원하는 데이터가 캐시에 있음. **Miss**: 없어서 하위 계층에서 가져와야 함.
- **평균 메모리 접근 시간(AMAT)** = 히트 시간 + 미스율 × 미스 페널티
- 예: 히트 1ns, 미스율 5%, 미스 페널티 100ns → 1 + 0.05×100 = **6ns**

**미스의 3C 분류**
1. **Compulsory(강제)**: 처음 접근하므로 반드시 발생. Cold miss라고도 한다.
2. **Capacity(용량)**: 작업 집합이 캐시보다 커서 발생.
3. **Conflict(충돌)**: 서로 다른 주소가 같은 위치에 매핑되어 발생.

멀티코어에서는 여기에 **Coherence miss**(다른 코어가 데이터를 수정해 무효화됨)가 더해진다.

## 4. 매핑 방식
메모리 블록을 캐시의 어느 위치에 둘지 정하는 방식이다. 주소는 **태그 | 인덱스 | 오프셋**으로 나뉜다.

| 방식 | 특징 | 장점 | 단점 |
|---|---|---|---|
| Direct Mapped | 블록이 정확히 한 위치에만 | 구현 단순, 빠름 | 충돌 미스 많음 |
| Fully Associative | 어느 위치든 가능 | 충돌 미스 최소 | 모든 태그 비교, 비용·전력 큼 |
| N-way Set Associative | 한 세트 내 N개 중 선택 | 절충안, 실무 표준 | 복잡도 증가 |

## 5. 교체 정책
캐시가 가득 찼을 때 어떤 라인을 내보낼지 결정한다.
- **LRU**: 가장 오래 사용되지 않은 것 제거. 성능이 좋지만 추적 비용이 크다(실제로는 근사 LRU 사용).
- **FIFO**: 가장 먼저 들어온 것 제거. 단순하다.
- **Random**: 무작위. 하드웨어가 간단하다.
- **LFU**: 사용 빈도가 가장 낮은 것 제거.

## 6. 쓰기 정책
- **Write-Through**: 쓸 때 캐시와 메모리에 동시에 기록. 일관성은 쉽지만 느리다. 보통 Write Buffer로 완화한다.
- **Write-Back**: 캐시에만 쓰고 **Dirty bit**를 세팅, 교체될 때 메모리에 반영. 빠르지만 일관성 관리가 복잡하다.
- **Write Allocate**: 쓰기 미스 시 블록을 캐시에 올린 뒤 쓴다(주로 Write-Back과 조합).
- **No-Write Allocate**: 캐시에 올리지 않고 메모리에 직접 쓴다(주로 Write-Through와 조합).

## 7. 캐시 일관성(Coherence)
멀티코어에서 각 코어의 L1/L2가 같은 주소의 복사본을 가질 때 값이 어긋나는 문제를 해결하는 프로토콜이다. 대표적인 것이 **MESI**다.

- **M**odified: 내 캐시만 수정된 상태(메모리와 다름)
- **E**xclusive: 내 캐시만 가지며 메모리와 같음
- **S**hared: 여러 캐시가 공유, 메모리와 같음
- **I**nvalid: 유효하지 않음

한 코어가 쓰면 다른 코어의 해당 라인은 Invalid로 바뀐다. 구현은 버스 **스누핑**이나 **디렉터리 기반** 방식이다.

### False Sharing
서로 다른 변수가 같은 캐시 라인에 있고 다른 코어가 각각 수정하면, 논리적으로 무관한데도 라인이 계속 무효화되어 성능이 급락한다. 해결책은 **패딩/정렬**(`alignas(64)`, Java의 `@Contended`)로 변수를 라인 단위로 분리하는 것이다.

## 8. 코드 최적화 관점
- 2차원 배열은 **행 우선(row-major)** 순서로 순회한다. C/Java는 행 방향이 메모리상 연속이다.
- 연결 리스트보다 배열이 캐시 친화적이다(포인터 추적은 지역성이 낮다).
- 구조체는 자주 같이 쓰는 필드를 모으고(**AoS vs SoA** 고려), 블로킹(타일링)으로 작업 집합을 줄인다.

## 9. 면접 예상 질문
1. **캐시가 왜 필요한가?** CPU-메모리 속도 격차(메모리 병목)를 지역성으로 완화하기 위해.
2. **Direct Mapped와 Set Associative 차이는?** 블록이 갈 수 있는 위치의 수. 연관도가 높을수록 충돌 미스는 줄지만 비교 비용이 증가한다.
3. **Write-Back의 장단점은?** 메모리 쓰기 횟수가 줄어 빠르지만, Dirty 관리와 일관성 처리가 복잡하다.
4. **False Sharing이란?** 같은 캐시 라인을 공유하는 서로 다른 변수 때문에 불필요한 무효화가 발생하는 현상.
5. **캐시와 TLB의 관계는?** TLB는 주소 변환 결과를 캐싱하는 별도 캐시다. 가상 주소 변환 비용을 줄인다.
6. **애플리케이션 캐시(Redis 등)와의 공통점은?** 둘 다 느린 저장소 앞의 빠른 저장소이며, 교체 정책·일관성·쓰기 정책 문제를 공유한다.

## 10. 한 줄 요약
> 캐시는 **지역성**을 이용해 느린 메모리 접근을 숨기는 장치이며, 매핑·교체·쓰기 정책과 멀티코어 **일관성**을 이해하는 것이 핵심이다.
