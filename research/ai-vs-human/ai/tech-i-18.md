# 인증방식

## 1. 인증과 인가의 차이
- **인증(Authentication)**: "너는 누구인가?"를 확인한다. 아이디와 비밀번호, 생체 정보, 인증서 등으로 신원을 증명한다.
- **인가(Authorization)**: "너는 무엇을 할 수 있는가?"를 결정한다. 인증이 끝난 뒤 권한(role, scope)을 검사한다.
- 응답 코드로는 인증 실패가 401 Unauthorized, 인가 실패가 403 Forbidden이다.

## 2. 세션-쿠키 기반 인증 (Stateful)
1. 로그인하면 서버가 사용자 정보를 세션 저장소(메모리, Redis, DB)에 보관한다.
2. 서버는 세션 ID를 `Set-Cookie` 헤더로 브라우저에 전달한다.
3. 이후 요청마다 브라우저가 쿠키를 자동으로 보내고, 서버는 세션 ID로 상태를 조회한다.
- **장점**: 서버가 세션을 즉시 무효화할 수 있어 강제 로그아웃이 쉽다.
- **단점**: 서버를 여러 대 두면 Redis 같은 공유 세션 저장소가 필요하다.
- **보안 속성**: `HttpOnly`(XSS로 쿠키 탈취 방지), `Secure`(HTTPS에서만 전송), `SameSite`(CSRF 완화)를 함께 설정한다.

## 3. 토큰 기반 인증 (Stateless, JWT)
JWT(JSON Web Token)는 `Header.Payload.Signature`를 Base64URL로 인코딩해 점(.)으로 이은 문자열이다.
- 서버는 서명(HMAC 또는 RSA/ECDSA)만 검증하면 되므로 세션 저장소가 필요 없다.
- Payload에는 `sub`, `exp`, `iat`, `role` 같은 클레임이 들어간다. Payload는 **암호화가 아니라 인코딩**이므로 민감 정보를 넣으면 안 된다.
- **한계**: 만료(`exp`) 전에는 폐기하기 어렵다. 그래서 Access Token의 수명을 짧게(예: 15분) 두고, Refresh Token으로 재발급받는다. Refresh Token은 서버에 저장하고 사용할 때마다 교체(rotation)해 재사용을 탐지한다.
- `alg: none` 공격과 서명 검증 누락을 막으려면 허용 알고리즘을 서버에서 고정해야 한다.

## 4. OAuth 2.0과 OpenID Connect
- **OAuth 2.0**은 *인가* 프레임워크다. 비밀번호를 제3자 앱에 넘기지 않고, 제한된 scope의 Access Token을 발급받는다.
- **OpenID Connect(OIDC)**는 OAuth 2.0 위에 얹은 *인증* 계층이다. 사용자 신원을 담은 `ID Token`(JWT)을 제공한다.
- 현재 권장 흐름은 **Authorization Code + PKCE**다. 클라이언트가 `code_verifier`에서 만든 `code_challenge`를 보내고, 일회성 `code`를 받은 뒤 `code_verifier`와 함께 토큰으로 교환한다. 이 흐름은 Implicit 흐름을 대체한다.

## 5. 기타 인증 방식
- **API Key**: 호출 주체를 식별하는 데 쓴다. 사용자 인증이라기보다 앱 식별에 가깝고, 노출되면 즉시 재발급해야 한다.
- **Basic 인증**: `Authorization: Basic base64(id:pw)` 형태다. 매 요청마다 자격 증명을 보내므로 반드시 HTTPS와 함께 쓴다.
- **Digest 인증**: nonce 기반 해시를 보내 Basic보다 안전하지만, 현재는 거의 쓰지 않는다.
- **mTLS**: 클라이언트 인증서로 상호 인증한다. 마이크로서비스 간 통신에서 자주 쓴다.
- **SSO(Single Sign-On)**: 한 번의 로그인으로 여러 서비스에 접근하며, 보통 SAML이나 OIDC로 구현한다.

## 6. 다중 요소 인증(MFA)
지식(비밀번호), 소유(OTP 앱, 보안키), 생체(지문, 얼굴) 중 둘 이상을 조합한다. TOTP는 30초마다 바뀌는 코드를 서버와 기기가 공유한 비밀키로 계산한다. 피싱에 강한 방식으로는 WebAuthn/FIDO2 기반 패스키가 있다.

## 7. 방식 비교

| 구분 | 세션-쿠키 | JWT | OAuth 2.0 / OIDC | API Key |
|---|---|---|---|---|
| 상태 관리 | Stateful | Stateless | 토큰 기반 | Stateless |
| 주 용도 | 웹 서비스 로그인 | API, 마이크로서비스 | 소셜 로그인, 위임 인가 | 서버 간 통신, 공개 API |
| 즉시 폐기 | 가능 | 만료 전 어려움 | 인가 서버에서 폐기 | 키 재발급 |
| 확장성 | 세션 저장소 필요 | 우수 | 우수 | 우수 |

## 8. 면접 예상 질문
- **세션과 JWT의 차이는?** 세션은 상태를 서버가 갖고 ID만 전달한다. JWT는 상태를 토큰에 담아 서버가 검증만 한다. 즉시 폐기 가능성과 확장성이 트레이드오프다.
- **JWT를 로컬 스토리지에 저장하면 안 되는 이유는?** XSS 공격으로 스크립트가 토큰을 읽을 수 있기 때문이다. `HttpOnly` 쿠키 저장을 고려한다.
- **OAuth 2.0만으로 로그인을 구현해도 되나?** 안 된다. OAuth는 인가 프레임워크라 사용자 신원을 보장하지 않는다. 로그인에는 OIDC의 ID Token을 사용해야 한다.

## 핵심 요약
- 인증은 신원 확인, 인가는 권한 확인이다.
- 웹 서비스는 세션-쿠키, API는 JWT, 제3자 연동은 OAuth 2.0/OIDC + PKCE가 일반적이다.
- 어떤 방식이든 HTTPS, 짧은 만료 시간, 안전한 저장, 서명 알고리즘 고정이 기본이다.
