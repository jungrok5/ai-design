# 우리 팀이 모노레포로 옮긴 이야기

> 저장소 14개를 하나로 합치기까지, 3개월 동안 배운 것들

안녕하세요. 프로덕트 플랫폼팀입니다.

올해 상반기, 저희 팀은 흩어져 있던 프론트엔드·백엔드·공용 라이브러리 저장소를 하나의 모노레포로 합쳤습니다. "모노레포가 좋다더라"는 이야기는 많이 들으셨겠지만, 실제로 옮기는 과정에서 무엇이 어려웠고 무엇이 좋아졌는지는 생각보다 잘 공유되지 않는 것 같습니다. 이 글에서는 저희가 **왜** 옮기기로 했는지, **어떻게** 옮겼는지, 그리고 **옮기고 나서 무엇이 달라졌는지**를 솔직하게 정리해 보려고 합니다.

---

## 1. 왜 옮기기로 했나

### 저장소가 늘어날수록 느려지던 개발

처음에는 서비스마다 저장소를 따로 두는 것이 자연스러웠습니다. 각 팀이 독립적으로 배포하고, 권한도 깔끔하게 나뉘었죠. 그런데 서비스가 늘어나면서 저장소도 14개까지 늘었고, 다음과 같은 문제가 반복되기 시작했습니다.

- **공용 라이브러리 수정 한 번에 PR이 여러 개.** 디자인 시스템 컴포넌트 하나를 고치면 라이브러리 저장소에 PR → 버전 배포 → 각 서비스 저장소에서 버전 올리는 PR을 따로 올려야 했습니다. 작은 수정이 며칠짜리 작업이 되곤 했습니다.
- **버전이 제각각.** 같은 공용 라이브러리를 서비스 A는 `2.3.0`, 서비스 B는 `1.8.4`로 쓰는 일이 흔했습니다. "이 버그는 이미 고쳤는데 왜 아직 나오지?"라는 질문이 자주 나왔습니다.
- **설정의 중복과 표류.** ESLint, TypeScript, CI 설정이 저장소마다 복사되어 있었고, 시간이 지나면서 조금씩 달라졌습니다. 규칙 하나를 바꾸려면 14번 같은 작업을 해야 했습니다.
- **변경의 영향 범위를 알기 어려움.** API 스키마를 바꿀 때 어떤 클라이언트가 영향을 받는지 확인하려면 여러 저장소를 일일이 뒤져야 했습니다.

### 모노레포에 기대한 것

저희가 모노레포에서 얻고 싶었던 것은 크게 세 가지였습니다.

1. **원자적 변경(atomic change)**: 라이브러리와 그것을 쓰는 서비스를 하나의 PR로 함께 수정하기
2. **단일 버전 정책**: 내부 패키지는 항상 최신 코드를 참조하기
3. **설정과 도구의 통합**: 린트·빌드·테스트 설정을 한 곳에서 관리하기

물론 걱정도 있었습니다. "빌드가 엄청 느려지지 않을까?", "CI가 매번 전체를 돌리면 어떡하지?", "권한 관리는?" 같은 질문들이었죠. 이 걱정들을 어떻게 풀었는지는 아래에서 이어서 이야기하겠습니다.

## 2. 도구 선택

여러 도구를 비교한 끝에 저희는 다음 조합을 골랐습니다.

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 패키지 매니저 | **pnpm workspaces** | 빠른 설치, 엄격한 의존성 관리, 디스크 절약 |
| 태스크 러너 / 캐시 | **Turborepo** | 설정이 단순하고, 원격 캐시를 쉽게 붙일 수 있음 |
| 백엔드 빌드 | 기존 Gradle 유지 | 무리하게 하나의 빌드 도구로 통일하지 않음 |

Nx와 Bazel도 검토했습니다. Nx는 기능이 풍부했지만 저희 규모에서는 학습 비용이 더 크다고 판단했고, Bazel은 강력하지만 팀 전체가 익숙해지기까지 시간이 너무 오래 걸릴 것 같았습니다. **"지금 우리 팀이 감당할 수 있는 복잡도"**를 가장 중요한 기준으로 삼았습니다.

최종 디렉터리 구조는 다음과 같습니다.

```text
.
├── apps/
│   ├── web/              # 사용자용 웹
│   ├── admin/            # 어드민
│   └── api/              # 백엔드 API
├── packages/
│   ├── ui/               # 디자인 시스템
│   ├── api-client/       # API 스키마에서 생성한 클라이언트
│   ├── utils/
│   └── config/           # eslint, tsconfig 등 공용 설정
├── turbo.json
├── pnpm-workspace.yaml
└── package.json
```

## 3. 어떻게 옮겼나

### 원칙: 한 번에 옮기지 않는다

가장 먼저 정한 원칙은 **"빅뱅 이전은 하지 않는다"**였습니다. 모든 저장소를 하루아침에 합치면 문제가 생겼을 때 원인을 찾기 어렵고, 그동안 기능 개발도 멈춰야 합니다. 그래서 의존성이 가장 적은 저장소부터 하나씩 옮겼습니다.

1. **공용 설정(`config`)과 유틸(`utils`)** — 다른 곳에 의존하지 않아 가장 안전
2. **디자인 시스템(`ui`)** — 가장 많이 쓰이는 라이브러리, 효과를 빨리 체감
3. **어드민 앱** — 트래픽이 적어 문제가 생겨도 영향이 작음
4. **사용자용 웹, API** — 마지막에, 충분히 검증된 뒤에

### Git 히스토리 보존하기

"옮기면서 커밋 히스토리가 날아가는 것 아니냐"는 질문을 가장 많이 받았습니다. 저희는 `git filter-repo`로 각 저장소의 파일 경로를 새 위치로 바꾼 뒤 모노레포에 병합하는 방식을 썼습니다.

```bash
# 1) 기존 저장소를 복제하고, 모든 파일을 packages/ui/ 아래로 옮긴 히스토리로 재작성
git clone git@github.com:our-org/ui.git ui-migrate
cd ui-migrate
git filter-repo --to-subdirectory-filter packages/ui

# 2) 모노레포에서 재작성된 저장소를 가져와 병합
cd ../monorepo
git remote add ui ../ui-migrate
git fetch ui
git merge ui/main --allow-unrelated-histories -m "chore: import ui repository"
git remote remove ui
```

이렇게 하면 `git log packages/ui`나 `git blame`으로 예전 기록을 그대로 따라갈 수 있습니다.

### 이전 기간 동안의 동기화

옮기는 도중에도 기존 저장소에서 개발은 계속됐습니다. 그래서 이전 대상 저장소는 **이전 직전 1주일 동안 코드 프리즈**를 걸고, 이전이 끝나면 기존 저장소를 읽기 전용(archive)으로 바꿨습니다. 저장소 README 맨 위에는 새 위치를 안내하는 문구를 남겼습니다.

## 4. 걱정했던 문제들, 이렇게 풀었습니다

### "CI가 너무 느려지지 않을까?"

가장 큰 걱정이었고, 실제로 첫 주에는 문제가 됐습니다. PR 하나에 모든 패키지의 테스트가 돌면서 CI 시간이 크게 늘었거든요. 두 가지로 해결했습니다.

**① 변경된 패키지와 그 의존 패키지만 실행하기**

```bash
turbo run lint test build --filter="...[origin/main]"
```

`...[origin/main]` 필터는 main 대비 바뀐 패키지와, 그 패키지에 의존하는 패키지만 골라 실행합니다. 디자인 시스템을 고치면 그걸 쓰는 앱들까지 함께 검증되고, 관계없는 앱은 건너뜁니다.

**② 원격 캐시 사용하기**

Turborepo 원격 캐시를 붙여서, 누군가 이미 같은 입력으로 빌드한 결과가 있으면 다시 빌드하지 않도록 했습니다. 로컬에서 빌드한 결과도 CI와 공유되기 때문에 체감 효과가 컸습니다.

```json
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**", "!.next/cache/**"]
    },
    "test": {
      "dependsOn": ["^build"]
    },
    "lint": {}
  }
}
```

### "코드 리뷰 담당은 어떻게 나누지?"

저장소가 하나가 되면서 "누가 어떤 코드를 리뷰해야 하는지"가 흐려질 수 있었습니다. GitHub의 `CODEOWNERS`로 디렉터리별 담당 팀을 지정해 해결했습니다.

```text
/apps/web/        @our-org/web-team
/apps/admin/      @our-org/admin-team
/apps/api/        @our-org/backend-team
/packages/ui/     @our-org/design-system
/packages/config/ @our-org/platform
```

### "배포는 따로 할 수 있나?"

네, 할 수 있습니다. 모노레포는 **코드를 한 곳에 두는 것**일 뿐, 배포까지 하나로 묶을 필요는 없습니다. 각 앱의 배포 워크플로는 해당 경로(와 그 앱이 의존하는 패키지)가 바뀌었을 때만 실행되도록 했습니다.

## 5. 옮기고 나서 달라진 것

이전을 마치고 몇 달이 지난 지금, 가장 크게 체감하는 변화들입니다.

- **공용 라이브러리 수정이 PR 하나로 끝납니다.** 예전에는 여러 저장소를 오가며 며칠 걸리던 작업이, 이제는 하나의 PR에서 라이브러리와 사용처를 함께 고치고 함께 리뷰받습니다.
- **"버전 안 맞음" 문제가 사라졌습니다.** 내부 패키지는 `workspace:*`로 참조하기 때문에 항상 같은 코드를 씁니다.
- **CI 시간이 오히려 줄었습니다.** 변경 감지와 원격 캐시 덕분에, 대부분의 PR은 이전보다 빨리 끝납니다.
- **신규 입사자 온보딩이 쉬워졌습니다.** `git clone` 한 번, `pnpm install` 한 번이면 전체 서비스를 로컬에서 띄울 수 있습니다.
- **리팩터링에 대한 두려움이 줄었습니다.** 타입 체크가 전체 코드베이스에 걸쳐 동작하니, API 스키마를 바꾸면 영향받는 곳이 바로 컴파일 에러로 드러납니다.

물론 아쉬운 점도 있습니다.

- **저장소 크기**: clone이 예전보다 무거워졌습니다. CI에서는 shallow clone과 sparse checkout으로 대응하고 있습니다.
- **IDE 성능**: 저장소 전체를 열면 TypeScript 언어 서버가 느려질 때가 있어서, 필요한 앱 폴더만 여는 것을 권장하고 있습니다.
- **공용 영역의 책임**: 루트 설정이나 공용 패키지를 바꾸면 모든 팀이 영향을 받기 때문에, 플랫폼팀의 리뷰 부담이 늘었습니다.

---

## 6. 모노레포를 고민하는 팀에게

마지막으로, 저희 경험에서 얻은 조언을 정리해 봅니다.

1. **문제부터 정의하세요.** "다들 모노레포를 쓰니까"가 아니라 "우리는 공용 코드 변경이 너무 느리다"처럼 구체적인 문제가 있어야, 옮긴 뒤에 효과를 판단할 수 있습니다.
2. **팀이 감당할 수 있는 도구를 고르세요.** 가장 강력한 도구가 아니라, 우리 팀이 유지보수할 수 있는 도구가 정답입니다.
3. **점진적으로 옮기세요.** 의존성이 적은 것부터, 영향이 작은 것부터 옮기면 위험을 크게 줄일 수 있습니다.
4. **CI 최적화는 처음부터 계획하세요.** 변경 감지와 캐시 없이 모노레포를 운영하면 금방 CI가 병목이 됩니다.
5. **소유권을 명확히 하세요.** `CODEOWNERS`와 디렉터리 규칙을 미리 정해 두면 "이건 누구 코드지?"라는 혼란을 막을 수 있습니다.

모노레포는 만능이 아닙니다. 하지만 여러 저장소 사이를 오가느라 지쳐 있던 저희 팀에게는 분명히 좋은 선택이었습니다. 비슷한 고민을 하고 계신 분들께 이 글이 작은 참고가 되었으면 좋겠습니다.

읽어 주셔서 감사합니다. 궁금한 점이 있다면 언제든 댓글로 남겨 주세요!
