# 우리 팀이 모노레포로 옮긴 이야기

> 이 글은 우리 팀이 여러 개의 저장소를 하나의 모노레포로 합치면서 겪은 과정을 정리한 기록입니다. 같은 고민을 하고 계신 분들에게 참고가 되었으면 합니다.

## 시작은 작은 불편함이었습니다

처음에는 불편이 작았습니다. 웹 앱, 공통 UI 라이브러리, API 서버가 각각 다른 저장소에 있었고, 기능 하나를 바꾸려면 저장소 세 개를 오가며 PR을 올려야 했습니다. 공통 라이브러리를 고치면 버전을 올리고, 배포하고, 다시 앱에서 버전을 맞추는 일이 반복되었습니다.

어느 날 한 기능을 배포하는 데 하루가 걸렸습니다. 원인은 코드가 아니라 저장소 사이의 의존성 동기화였습니다. 그때 팀원 몇 명이 같은 이야기를 꺼냈습니다. "이 과정을 줄일 방법이 있지 않을까요?"

## 왜 모노레포인가

여러 방법을 비교했습니다. 저장소를 계속 나누고 패키지 레지스트리로 연결하는 방법도 있었지만, 우리에게는 다음 이유가 더 컸습니다.

- **원자적 변경**: API 응답 형식을 바꾸면서 클라이언트도 한 PR에서 같이 고칠 수 있어야 했습니다.
- **공유 코드의 즉시 반영**: 공통 라이브러리 수정이 앱에 바로 반영되어야 했습니다.
- **도구 통일**: 린트, 테스트, CI 설정을 프로젝트마다 따로 관리하던 부담을 줄이고 싶었습니다.

반대로 모노레포가 공짜가 아니라는 것도 알고 있었습니다. CI 실행 시간이 길어지고, 저장소 크기가 커지고, 접근 권한을 세분화하기 어려워집니다. 우리는 이 비용을 감수할 만한지 먼저 확인하기로 했습니다.

## 옮기기 전에 한 일

바로 옮기지 않고 두 가지를 먼저 했습니다.

1. **의존성 그래프 그리기**: 어떤 패키지가 어떤 패키지를 참조하는지 표로 정리했습니다. 생각보다 순환 참조가 있었고, 이것부터 끊어야 했습니다.
2. **변경 빈도 조사**: 최근 6개월 커밋 기록을 보니 같은 시기에 여러 저장소가 함께 바뀌는 경우가 많았습니다. 하나로 묶는 것이 실제 작업 흐름에 맞는다고 판단했습니다.

이 단계에서 팀 전체가 합의한 원칙도 세웠습니다. 히스토리는 `git subtree`로 보존하고, 기존 저장소는 한 달 동안 읽기 전용으로 남겨 둡니다.

## 옮기는 과정

한 번에 옮기지 않고 단계를 나눴습니다.

- **1단계**: 공통 라이브러리를 `packages/`로 옮기고, 기존 저장소에서 참조하도록 설정했습니다.
- **2단계**: API 서버와 웹 앱을 `apps/` 아래로 옮겼습니다. 이때 CI 파이프라인을 변경된 패키지만 빌드하도록 바꿨습니다.
- **3단계**: 기존 저장소를 정리하고, 문서와 배포 절차를 새 구조에 맞췄습니다.

각 단계가 끝날 때마다 배포를 한 번씩 확인했습니다. 한 번에 모든 것을 바꾸면 문제가 생겼을 때 원인을 찾기 어렵기 때문입니다.

## 겪은 문제들

계획대로만 진행되지는 않았습니다.

**CI 시간이 늘어났습니다.** 처음에는 모든 테스트가 모든 변경에 대해 돌았습니다. 변경 영향 범위를 계산해서 바뀐 패키지와 그에 의존하는 패키지만 테스트하도록 바꾸자 평균 빌드 시간이 크게 줄었습니다. 구체적인 수치는 팀 내부 기준이 달라서 생략하겠습니다.

**버전 관리 방식을 정해야 했습니다.** 패키지마다 버전을 따로 올릴지, 저장소 전체를 하나의 버전으로 볼지 논의가 길어졌습니다. 결국 내부 패키지는 버전 없이 워크스페이스 링크로 참조하고, 외부에 배포하는 패키지만 별도로 버전을 관리하기로 했습니다.

**코드 소유권이 흐려졌습니다.** 한 저장소 안에 여러 팀의 코드가 있다 보니 리뷰어를 누구로 해야 할지 헷갈렸습니다. `CODEOWNERS` 파일을 만들어 디렉터리별 담당자를 명시했습니다.

**옛 습관이 남았습니다.** 어떤 팀원은 여전히 공통 라이브러리를 복사해서 쓰려 했습니다. 이 문제는 기술보다 설명과 리뷰로 해결해야 했습니다.

## 얻은 것

시간이 지나고 보니 가장 큰 변화는 작업 흐름이었습니다.

- API와 클라이언트를 한 PR에서 함께 고칠 수 있게 되었습니다.
- 공통 코드 수정이 즉시 반영되어, 버전 동기화 작업이 사라졌습니다.
- 린트와 테스트 설정을 한 곳에서 관리하게 되었습니다.
- 새로 합류한 팀원이 전체 구조를 한 저장소에서 파악할 수 있게 되었습니다.

## 아쉬운 점

모노레포가 모든 문제를 해결하지는 않았습니다. 저장소가 커지면서 로컬 클론과 IDE 인덱싱이 느려졌고, 빌드 도구 설정을 이해하는 사람이 몇 명으로 한정되는 문제도 있습니다. 이 부분은 계속 개선하고 있습니다.

## 마치며

모노레포는 목적이 아니라 수단입니다. 우리가 원했던 것은 "변경을 빠르고 안전하게 배포하는 것"이었고, 모노레포는 그 목표에 맞는 선택이었습니다. 같은 고민을 하고 계신다면, 먼저 현재 저장소 사이의 의존성과 변경 패턴부터 살펴보시길 권합니다. 도구를 바꾸기 전에 문제를 정확히 보는 것이 가장 중요했습니다.

읽어 주셔서 감사합니다.
