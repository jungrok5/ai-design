1. 첫 주 할 일

첫 주의 목표는 로컬에서 프로젝트를 실행하고, 작은 변경을 PR로 올려 리뷰를 받아보는 것입니다. 속도보다 흐름을 익히는 데 집중하세요.

Day 1

오리엔테이션

  • 팀장·멘토와 1:1 인사
  • 계정 발급 확인 (메일, 사내 메신저, Git, 이슈 트래커)
  • 보안 교육 및 서약
  • 이 가이드 끝까지 읽기
Day 2

개발 환경 세팅

  • 아래 2장의 순서대로 설치
  • 저장소 clone 후 로컬 실행
  • 테스트 한 번 돌려보기
Day 3

코드베이스 파악

  • README, 아키텍처 문서 읽기
  • 멘토와 함께 최근 PR 2~3개 같이 보기
  • 주요 디렉터리 구조 메모
Day 4

첫 PR 올리기

  • 문서 오타 수정 또는 아주 작은 버그 한 건 선택
  • 브랜치 생성 → 수정 → PR 작성
  • 셀프 리뷰 후 리뷰 요청
Day 5

리뷰 반영 & 회고

  • 받은 코멘트 반영 후 머지
  • 멘토와 한 주 회고 (잘 된 것, 막힌 것)
  • 다음 주 목표 합의
막히면 바로 물어보세요. 30분 이상 혼자 붙잡고 있는 것은 도움이 되지 않습니다. 질문은 언제든 환영입니다.

2. 개발 환경 세팅

아래 순서대로 진행하세요. 각 명령어 우측의 복사 버튼으로 바로 복사할 수 있습니다.

필수 도구 설치

아래 도구를 설치합니다. 버전은 팀 문서의 권장 버전을 따르세요.

도구용도확인 명령
Git소스 버전 관리git --version
런타임 (팀 지정)애플리케이션 실행[런타임] --version
Docker로컬 DB·의존 서비스 실행docker --version
IDE / 에디터코드 작성팀 권장 에디터 (린터·포매터 플러그인 설치)

Git 기본 설정

커밋에 남을 이름과 이메일을 회사 계정으로 맞춥니다.

git config --global user.name "홍길동"
git config --global user.email "gildong.hong@company.com"
git config --global pull.rebase true

저장소 clone 및 의존성 설치

git clone <저장소 URL>
cd <프로젝트 폴더>
<패키지 매니저> install   # 예: npm install, pip install -r requirements.txt

환경 변수 설정

비밀 값은 저장소에 커밋하지 않습니다. 예시 파일을 복사해 로컬 값만 채웁니다.

cp .env.example .env
# .env 파일을 열어 개발용 값 입력 (값은 팀 비밀 저장소에서 확인)
주의: .env 파일은 절대 커밋하지 마세요. 실수로 커밋했다면 즉시 멘토에게 알려 주세요.

로컬 DB 및 서비스 실행

docker compose up -d
<실행 명령>        # 예: npm run dev
<테스트 명령>      # 예: npm test

브라우저에서 http://localhost:<포트>에 접속해 화면이 뜨면 세팅 완료입니다.

문제 해결 팁

  • 포트 충돌: 이미 같은 포트를 쓰는 프로세스가 있는지 확인하고 종료합니다.
  • 의존성 오류: 런타임 버전이 팀 권장 버전과 맞는지 확인합니다.
  • Docker 실행 실패: Docker Desktop이 켜져 있는지 확인합니다.
  • 그래도 안 되면: 에러 전문과 실행 명령을 함께 멘토에게 공유하세요.

3. 코드 리뷰 규칙

리뷰의 목적은 코드의 품질을 높이고 팀이 같은 코드를 이해하도록 돕는 것입니다. 사람이 아니라 코드를 평가합니다.

3-1. 작성자(PR 올리는 사람)의 책임

  1. 셀프 리뷰 먼저: 올리기 전에 diff를 직접 한 번 읽고 불필요한 변경, 디버그 코드, 주석 처리된 코드를 지웁니다.
  2. CI 통과 확인: 빌드, 린트, 테스트가 모두 통과한 뒤 리뷰를 요청합니다.
  3. PR 크기: 변경 줄 수는 400줄 이내를 권장합니다. 넘으면 나눠서 올립니다.
  4. 설명 작성: 무엇을, 왜 바꿨는지, 어떻게 확인했는지, 리뷰어가 특히 봐야 할 부분을 적습니다.
  5. 빠른 응답: 코멘트에는 해당 반영 여부를 답변으로 남깁니다. 반영하지 않으면 이유를 적습니다.

3-2. PR 제목 및 브랜치 이름

브랜치:  feature/<이슈번호>-<짧은-설명>   예) feature/123-login-validation
         fix/<이슈번호>-<짧은-설명>       예) fix/456-null-pointer-on-logout

PR 제목: [<이슈번호>] <변경 요약>       예) [123] 로그인 폼 이메일 검증 추가

3-3. 리뷰어의 책임

  • 요청을 받으면 1 영업일 이내에 첫 리뷰를 남깁니다. 바빠서 늦어지면 미리 알립니다.
  • 코드의 정확성, 가독성, 테스트, 보안 측면을 중심으로 봅니다.
  • 취향 차이는 강요하지 않습니다. 팀 컨벤션에 없는 스타일 문제는 린터에 맡깁니다.
  • 문제만 지적하지 말고 가능하면 대안이나 이유를 함께 씁니다.
  • 승인(Approve)은 최소 1명의 리뷰를 받은 뒤, 남은 코멘트를 모두 해결했을 때 합니다.

3-4. 코멘트 라벨

코멘트 앞에 라벨을 붙이면 작성자가 우선순위를 바로 알 수 있습니다.

blocker:반드시 고쳐야 머지할 수 있음 (버그, 보안, 데이터 손실)
suggestion:더 나은 방법이 있다는 제안. 반영 여부는 작성자가 판단
question:이해가 안 되는 부분 질문. 답변이 곧 코드 설명이 됨
nit:사소한 취향·오타. 반영하지 않아도 머지 가능
praise:잘한 부분 칭찬. 신입이라면 꼭 받아 보세요

3-5. 머지 전 확인 사항

  • CI 전 항목 통과
  • 승인 1건 이상, blocker: 코멘트 모두 해결
  • 관련 문서(README, API 문서 등) 갱신 여부 확인
  • DB 스키마 변경이 있다면 마이그레이션 파일 포함 여부 확인
  • 머지는 작성자가 직접 합니다 (리뷰어가 승인 후 작성자가 머지)
리뷰 중 감정이 상했다면? 코드에 대한 피드백은 사람에 대한 평가가 아닙니다. 이해가 안 되면 댓글보다 짧은 대화(메신저, 통화)로 바로 풀어 보세요.
