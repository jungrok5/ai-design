# 우리 팀이 모노레포로 옮긴 이야기
우리 팀은 [TODO: 기간] 동안 저장소 [TODO: N]개에 나뉘어 있던 코드를 단일 저장소로 합쳤습니다. 이 글은 옮기기로 한 이유, 옮긴 순서, 옮긴 뒤 바뀐 점과 아직 풀지 못한 문제를 정리합니다.
## 저장소가 여러 개일 때 생긴 문제
저장소를 서비스마다 하나씩 두던 시절에는 공통 코드를 내부 패키지로 배포해 각 저장소가 버전을 지정해 가져다 썼습니다. 공통 패키지를 고치면 다음 작업이 따라왔습니다.
1. 공통 패키지 저장소에서 수정하고 새 버전을 배포합니다.
2. 그 패키지를 쓰는 저장소마다 버전을 올리는 PR을 엽니다.
3. 저장소마다 CI를 따로 통과시키고 따로 배포합니다.
변경 한 건이 PR [TODO: N]개로 흩어졌고, 일부 저장소는 버전 업데이트가 밀려 같은 패키지의 서로 다른 버전이 운영 환경에 함께 떠 있었습니다. 린트 규칙, TypeScript 설정, CI 스크립트도 저장소마다 조금씩 달라서 한 저장소에서 통하던 코드가 다른 저장소에서 빌드에 실패하는 일이 반복됐습니다.
## 모노레포를 고른 기준
대안으로 검토한 방식과 판단 근거는 다음과 같습니다.
| 방식 | 장점 | 우리 팀에서 걸린 점 |
| 저장소 분리 유지 + 자동 버전 업데이트 봇 | 기존 구조를 바꾸지 않음 | PR 수는 줄지 않고 리뷰할 사람만 바뀜 |
| Git 서브모듈 | 저장소를 나눈 채로 코드 공유 | 커밋 포인터 관리가 번거롭고 팀원 대부분이 익숙하지 않음 |
| 모노레포 | 변경을 커밋 한 번에 처리, 설정 통일 | 빌드·CI 시간이 저장소 크기에 따라 늘어남 |
모노레포의 단점인 빌드 시간은 변경된 패키지만 빌드하고 결과를 캐시하는 도구로 줄일 수 있다고 판단했습니다. 우리 팀은 [TODO: 패키지 매니저]의 워크스페이스 기능과 [TODO: 빌드 도구]를 쓰기로 했습니다.
## 저장소 구조
배포 단위는 `apps/` 아래에, 여러 앱이 함께 쓰는 코드는 `packages/` 아래에 둡니다. 앱이 공통 패키지를 쓸 때는 배포된 버전이 아니라 워크스페이스 안의 소스를 바로 참조합니다.
## 옮긴 순서
한 번에 모든 저장소를 합치지 않고 의존 관계가 적은 저장소부터 하나씩 옮겼습니다.
1. 빈 모노레포를 만들고 공통 설정을 `packages/config`에 모았습니다.
2. 공통 패키지 저장소를 먼저 옮겼습니다. 이 단계에서는 기존 저장소들이 계속 배포된 버전을 쓸 수 있도록 패키지 배포를 유지했습니다.
3. 서비스 저장소를 하나씩 `apps/`로 옮겼습니다. 커밋 기록을 보존하려고 [TODO: 사용한 방법, 예: git subtree / git filter-repo]로 기존 기록을 가져왔습니다.
4. 옮긴 서비스의 CI와 배포 파이프라인을 모노레포 기준으로 다시 연결하고, 기존 저장소는 읽기 전용으로 바꿨습니다.
5. 모든 서비스를 옮긴 뒤 공통 패키지의 외부 배포를 중단했습니다.
저장소별로 옮기는 데 [TODO: 기간]이 걸렸고, 이전 기간 동안 기능 개발은 멈추지 않았습니다.
## 옮긴 뒤 달라진 점
공통 패키지를 고치는 변경이 PR 하나로 끝나게 됐습니다. 수정한 패키지와 그 패키지를 쓰는 앱이 같은 PR에서 함께 빌드되고 테스트되므로, 호환성이 깨지면 병합 전에 CI가 실패합니다.

## 아직 풀지 못한 문제
- 공통 패키지를 고치면 의존하는 앱 전체가 다시 빌드되어, 그런 PR은 CI 시간이 여전히 깁니다.
- 저장소 전체 권한이 한 곳에 모여 있어 코드 소유자(CODEOWNERS) 설정으로 리뷰어를 나누고 있지만, 경계가 애매한 디렉터리가 남아 있습니다.
- 저장소를 처음 클론하고 의존성을 설치하는 데 [TODO: 시간]이 걸립니다.
모노레포는 여러 서비스가 코드를 많이 공유하고, 한 팀이 그 서비스들을 함께 관리할 때 효과가 컸습니다. 서비스 사이에 공유 코드가 거의 없거나 팀마다 배포 주기가 크게 다르다면 저장소를 나눠 두는 쪽이 관리 부담이 더 적을 수 있습니다.
