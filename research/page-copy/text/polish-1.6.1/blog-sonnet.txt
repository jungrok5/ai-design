# 우리 팀이 모노레포로 옮긴 이야기
> 작성: [작성자] · [날짜]
> 읽는 시간: 약 7분
여러 레포지토리로 나뉘어 있던 우리 서비스를 모노레포 하나로 합친 과정을 정리했습니다. 옮긴 이유와 방법, 옮긴 뒤 달라진 점을 적었습니다.
> `[대괄호]`로 표시된 부분은 우리 팀의 실제 숫자와 이름으로 바꿔 주세요.
## 1. 모노레포로 옮긴 이유
옮기기 전 우리는 `[N]`개의 레포지토리를 운영하고 있었습니다.
- `web`: 프론트엔드
- `api`: 백엔드 서버
- `shared-types`: 공통 타입 정의 (npm 패키지로 배포)
- `ui-kit`: 공통 UI 컴포넌트 (npm 패키지로 배포)
- `infra`: 배포 및 인프라 설정
처음에는 레포가 나뉘어 있는 편이 깔끔해 보였습니다. 팀이 커지면서 아래 문제가 반복되었습니다.
### 1.1 작은 변경 하나에 PR이 세 개
API 응답 필드 하나를 추가하는 순서는 이랬습니다.
1. `shared-types`에 타입 추가 → PR → 리뷰 → 머지 → 버전 올려 배포
2. `api`에서 새 버전을 설치하고 구현 → PR
3. `web`에서 새 버전을 설치하고 화면 반영 → PR
코드 수정은 10분이면 끝나는데, 리뷰와 배포를 기다리는 시간이 하루를 넘기곤 했습니다.
### 1.2 버전 불일치
`web`은 `shared-types@1.4.0`을, `api`는 `1.3.2`를 쓰는 일이 종종 생겼습니다. 이 불일치는 런타임에서야 드러났습니다.
### 1.3 레포마다 다른 설정
ESLint, TypeScript, CI 설정은 처음에 같은 파일을 복사해서 시작했지만, 시간이 지나면서 레포마다 조금씩 달라졌습니다.
## 2. 도입 전에 고민한 것들
옮기기 전에 걱정되는 점을 먼저 적고, 각각에 대한 판단을 정리했습니다.
| 우려 | 우리의 판단 |
| CI 시간이 길어지지 않을까? | 변경된 패키지만 빌드/테스트하도록 구성하면 해결 가능 |
| 레포가 너무 커지지 않을까? | 현재 규모에서는 문제 없음. 커지면 그때 다시 논의 |
| 권한 분리가 어려워지지 않을까? | `CODEOWNERS`로 영역별 리뷰어 지정 |
| 마이그레이션 중 개발이 멈추지 않을까? | 단계적으로 옮기고 그동안 기존 레포도 유지 |
### 도구 선택
후보는 아래 세 가지였습니다.
우리는 아래 이유로 `[선택한 도구]`를 골랐습니다.
- 설정이 단순해서 팀원이 빠르게 익힐 수 있다
- 캐시와 작업 의존성 그래프를 기본으로 제공한다
- 기존 `package.json` 스크립트를 크게 바꾸지 않아도 된다
## 3. 옮긴 방법
### 3.1 디렉터리 구조
`pnpm-workspace.yaml`은 이렇게 간단합니다.
### 3.2 git 히스토리 보존
파일만 복사하면 `git blame`과 과거 커밋 기록이 사라집니다. 그래서 각 레포의 히스토리를 하위 디렉터리 기준으로 재작성한 뒤 병합했습니다.
> `git filter-repo`는 별도로 설치해야 합니다. 히스토리를 재작성하므로 원본이 아닌 클론한 사본에서 실행하세요.
### 3.3 내부 패키지 참조
버전을 올려 배포하던 방식을 워크스페이스 참조로 바꿨습니다.
이제 `shared-types`를 수정하면 별도 배포나 버전 변경 없이 `web`과 `api`에 바로 반영됩니다.
### 3.4 변경된 부분만 빌드하기
`turbo.json`으로 작업 간 의존성을 선언했습니다.
CI에서는 변경에 영향받는 패키지만 실행합니다.
### 3.5 단계별 전환
한 번에 모두 옮기지 않고 아래 순서로 진행했습니다.
1. 공통 패키지: `shared-types`, `ui-kit`
2. 백엔드: `api`
3. 프론트엔드: `web`
4. 인프라: `infra`
5. 기존 레포는 읽기 전용으로 전환 후 아카이브
각 단계마다 최소 `[N]`일은 안정화 기간을 두었습니다.
## 4. 겪었던 문제들
### 4.1 CI 캐시가 안 먹었다
처음 며칠은 CI가 매번 전체를 빌드했습니다. CI 환경에서 캐시 디렉터리를 저장·복원하지 않았기 때문입니다. 원격 캐시를 연결한 뒤에야 의도한 속도가 나왔습니다.
### 4.2 의존성 호이스팅 문제
pnpm은 `package.json`에 선언하지 않은 패키지를 불러오지 못하게 합니다. 그래서 선언 없이 쓰던 패키지가 한꺼번에 에러로 나왔고, 이를 고치면서 빠져 있던 의존성 선언을 채웠습니다.
### 4.3 커밋 컨벤션과 릴리스
여러 앱이 한 레포에 있으니 커밋마다 어느 앱에 영향을 주는지 알아야 했습니다. 그래서 커밋 메시지에 스코프(`feat(web): ...`, `fix(api): ...`)를 붙이도록 규칙을 정했습니다.
## 5. 결과
옮기고 나서 `[기간]` 동안 지켜본 변화입니다.
| 항목 | 이전 | 이후 |
| 타입 변경이 포함된 기능 PR 수 | 평균 `[N]`개 | 1개 |
| 변경 → 모든 앱 반영까지 걸리는 시간 | `[N]` | `[N]` |
| CI 평균 소요 시간 | `[N]`분 | `[N]`분 |
| 공통 설정 불일치로 인한 이슈 | 월 `[N]`건 | 월 `[N]`건 |
표에 드러나지 않는 변화도 있었습니다.
- 리팩터링이 레포 경계에서 멈추지 않고 여러 패키지에 걸쳐 한 번에 진행된다
- 새로 합류한 사람이 클론 한 번으로 전체 구조를 볼 수 있다
- "이 패키지 어느 버전 쓰고 있어요?"라는 질문이 사라졌다
## 6. 모노레포가 맞는 팀과 맞지 않는 팀
**추천하는 경우**
- 레포 간 공통 코드(타입, 컴포넌트, 유틸)가 많다
- 하나의 기능이 보통 여러 레포를 동시에 건드린다
- 같은 팀이 대부분의 레포를 함께 관리한다
**신중해야 하는 경우**
- 레포별로 팀과 배포 주기가 완전히 독립적이다
- 접근 권한을 레포 단위로 엄격히 나눠야 한다
- 빌드 도구와 언어가 서로 전혀 다르다
우리 팀은 공통 코드가 많고 기능 하나가 여러 레포를 건드렸기 때문에 모노레포가 잘 맞았습니다. 다만 모든 팀에 맞는 선택은 아닙니다.
