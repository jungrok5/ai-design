# 우리 팀이 모노레포로 옮긴 이야기
> 저장소 14개를 3개월에 걸쳐 하나로 합친 과정과 결과
안녕하세요. 프로덕트 플랫폼팀입니다.
올해 상반기에 저희 팀은 프론트엔드, 백엔드, 공용 라이브러리 저장소를 모노레포로 합쳤습니다. 모노레포의 장점은 많이 알려져 있습니다. 하지만 실제로 옮길 때 무엇이 어려웠고 옮긴 뒤 무엇이 나아졌는지 다룬 글은 많지 않은 것 같습니다. 이 글에는 저희가 옮긴 이유와 방법, 옮긴 뒤 달라진 점과 아쉬운 점을 적었습니다.
## 1. 왜 옮기기로 했나
### 저장소가 늘어날수록 느려지던 개발
처음에는 서비스마다 저장소를 따로 두었습니다. 팀마다 따로 배포했고, 권한도 저장소 단위로 나뉘었습니다. 서비스가 늘면서 저장소가 14개가 되자 다음 문제가 반복됐습니다.
- 공용 라이브러리를 한 번 고치는 데 PR이 여러 개 필요했습니다. 디자인 시스템 컴포넌트 하나를 고치면 라이브러리 저장소에 PR을 올리고, 새 버전을 배포한 뒤, 서비스 저장소마다 버전을 올리는 PR을 따로 올렸습니다. 작은 수정이 며칠씩 걸렸습니다.
- 서비스마다 라이브러리 버전이 달랐습니다. 같은 공용 라이브러리를 서비스 A는 `2.3.0`, 서비스 B는 `1.8.4`로 쓰는 일이 흔했고, "이미 고친 버그가 왜 아직 나오지?"라는 질문이 자주 나왔습니다.
- 설정이 저장소마다 복사되어 조금씩 어긋났습니다. ESLint, TypeScript, CI 설정을 저장소마다 따로 관리했기 때문에 공통 규칙을 바꾸려면 같은 작업을 14번 해야 했습니다.
- 변경의 영향 범위를 확인하기 어려웠습니다. API 스키마를 바꿀 때 영향받는 클라이언트를 찾으려면 여러 저장소를 일일이 뒤져야 했습니다.
### 모노레포에 기대한 것
모노레포로 옮겨서 얻으려던 것은 다음과 같습니다.
1. 원자적 변경(atomic change): 라이브러리와 그 라이브러리를 쓰는 서비스를 PR 하나에서 함께 수정
2. 단일 버전 정책: 내부 패키지는 항상 최신 코드를 참조
3. 설정과 도구 통합: 린트, 빌드, 테스트 설정을 한 곳에서 관리
걱정도 있었습니다. 빌드가 크게 느려지지 않을지, CI가 매번 전체를 다시 돌리지 않을지, 권한은 어떻게 나눌지였습니다. 이 문제를 어떻게 풀었는지는 4장에 적었습니다.
## 2. 도구 선택
저희가 고른 도구 조합은 다음과 같습니다.
| 영역 | 선택 | 이유 |
| 패키지 매니저 | **pnpm workspaces** | 빠른 설치, 엄격한 의존성 관리, 디스크 사용량 절감 |
| 태스크 러너 / 캐시 | **Turborepo** | 단순한 설정, 원격 캐시 연동이 쉬움 |
| 백엔드 빌드 | 기존 Gradle 유지 | 백엔드까지 같은 빌드 도구로 바꾸지 않음 |
Nx와 Bazel도 검토했습니다. Nx는 기능이 많지만 저희 규모에서는 학습 비용이 크다고 판단했고 Bazel은 팀 전체가 익숙해지기까지 시간이 너무 오래 걸릴 것으로 봤습니다. 기준은 지금 저희 팀이 감당할 수 있는 복잡도였습니다.

## 3. 어떻게 옮겼나
### 원칙: 한 번에 옮기지 않는다
모든 저장소를 한꺼번에 합치면 문제가 생겼을 때 원인을 찾기 어렵고, 이전하는 동안 기능 개발도 멈춰야 합니다. 그래서 의존성이 적은 저장소부터 하나씩 옮겼습니다.
1. 공용 설정(`config`)과 유틸(`utils`): 다른 패키지에 의존하지 않아 가장 안전
2. 디자인 시스템(`ui`): 가장 많이 쓰이는 라이브러리라 효과를 빨리 확인할 수 있음
3. 어드민 앱: 트래픽이 적어 문제가 생겨도 영향이 작음
4. 사용자용 웹, API: 앞 단계에서 충분히 검증한 뒤 마지막에
### Git 히스토리 보존하기
가장 많이 받은 질문은 옮기면서 커밋 히스토리가 사라지지 않느냐는 것이었습니다. 저희는 `git filter-repo`로 각 저장소의 파일 경로를 새 위치로 바꾼 뒤 모노레포에 병합했습니다.
병합한 뒤에도 `git log packages/ui`나 `git blame`으로 예전 기록을 그대로 볼 수 있습니다.
### 이전 기간 동안의 동기화
이전하는 동안에도 기존 저장소에서 개발은 계속됐습니다. 그래서 저장소마다 이전 직전 1주일 동안 코드 프리즈를 걸었고, 이전이 끝나면 기존 저장소를 읽기 전용(archive)으로 바꿨습니다. 기존 저장소 README 맨 위에는 새 위치를 적어 두었습니다.
## 4. 걱정했던 문제와 해결 방법
### CI 실행 시간
가장 걱정한 부분이었고, 첫 주에는 실제로 문제가 됐습니다. PR마다 모든 패키지의 테스트가 돌아 CI 시간이 크게 늘었습니다. 다음 두 가지로 줄였습니다.
**① 변경된 패키지와 이에 의존하는 패키지만 실행**
`...[origin/main]` 필터는 main 대비 바뀐 패키지와, 그 패키지에 의존하는 패키지만 실행합니다. 디자인 시스템을 고치면 이를 쓰는 앱까지 검증하고, 관계없는 앱은 건너뜁니다.
**② 원격 캐시 사용**
Turborepo 원격 캐시를 연결해, 같은 입력으로 이미 빌드한 결과가 있으면 다시 빌드하지 않게 했습니다. 로컬에서 빌드한 결과도 CI와 공유되므로 로컬에서 한 번 빌드한 패키지는 CI에서 다시 빌드하지 않습니다. 태스크 설정(`turbo.json`)은 다음과 같습니다.
### 코드 리뷰 담당
저장소를 합치면 어떤 코드를 누가 리뷰할지 불분명해질 수 있었습니다. GitHub `CODEOWNERS`에 디렉터리별 담당 팀을 지정했습니다.
### 앱별 배포
모노레포는 코드를 한 저장소에 두는 방식이고, 배포까지 하나로 묶을 필요는 없습니다. 앱마다 배포 워크플로를 따로 두고, 해당 앱 경로나 그 앱이 의존하는 패키지가 바뀌었을 때만 실행되게 했습니다.
## 5. 옮기고 나서 달라진 것
이전을 마치고 몇 달 동안 쓰면서 달라진 점입니다.
- 공용 라이브러리를 고칠 때 PR을 여러 개 올리지 않습니다. 라이브러리와 사용처를 한 PR에서 함께 고치고 함께 리뷰받습니다.
- 버전 불일치가 없어졌습니다. 내부 패키지를 `workspace:*`로 참조하므로 모든 앱이 같은 코드를 씁니다.
- CI 시간이 오히려 줄었습니다. 변경된 패키지만 실행하고 원격 캐시를 쓰기 때문에 대부분의 PR에서 CI가 이전보다 빨리 끝납니다.
- 신규 입사자는 `git clone`과 `pnpm install`을 한 번씩 실행하면 전체 서비스를 로컬에서 띄울 수 있습니다.
- 리팩터링 부담이 줄었습니다. 타입 체크가 코드베이스 전체에 걸쳐 동작하므로, API 스키마를 바꾸면 영향받는 곳이 바로 컴파일 에러로 나타납니다.
반대로 코드가 한 저장소에 모이면서 생긴 문제도 있습니다.
- clone이 예전보다 무거워졌습니다. CI에서는 shallow clone과 sparse checkout을 씁니다.
- 저장소 전체를 IDE로 열면 TypeScript 언어 서버가 느려질 때가 있어서, 필요한 앱 폴더만 열도록 안내하고 있습니다.
- 루트 설정이나 공용 패키지를 바꾸면 모든 팀이 영향을 받기 때문에 플랫폼팀의 리뷰 부담이 늘었습니다.
## 6. 모노레포를 고민하는 팀에게
1. 해결할 문제를 먼저 정하세요. "다들 모노레포를 쓰니까"가 아니라 "공용 코드 변경이 너무 느리다"처럼 문제가 구체적이어야 옮긴 뒤에 효과를 판단할 수 있습니다.
2. 팀이 유지보수할 수 있는 도구를 고르세요. 저희가 Nx와 Bazel 대신 Turborepo를 고른 기준도 기능이 아니라 팀이 감당할 수 있는 복잡도였습니다.
3. 의존성이 적고 영향이 작은 저장소부터 옮기세요. 하나씩 옮기면 문제가 생겨도 원인을 찾기 쉽습니다.
4. CI 최적화를 처음부터 계획하세요. 변경 감지와 캐시가 없으면 저희 첫 주처럼 CI가 병목이 됩니다.
5. 소유권을 미리 정하세요. `CODEOWNERS`와 디렉터리 규칙을 정해 두면 담당자를 찾지 못해 리뷰가 멈추는 일이 없습니다.
모노레포에도 5장에 적은 단점이 있습니다. 그래도 여러 저장소를 오가며 같은 수정을 반복하던 저희 팀에는 맞는 선택이었습니다.
