# 우리 팀이 모노레포로 옮긴 이야기
> 웹 앱, 공통 UI 라이브러리, API 서버 저장소를 모노레포 하나로 합친 과정을 기록했습니다. 옮긴 순서와 중간에 생긴 문제, 아직 남은 문제를 적었습니다.
## 저장소 세 개를 오가던 배포
웹 앱, 공통 UI 라이브러리, API 서버가 각각 다른 저장소에 있었습니다. 기능 하나를 바꾸려면 저장소 세 개에 PR을 따로 올려야 했습니다. 공통 라이브러리를 고칠 때마다 버전을 올려 배포한 뒤 앱의 의존성 버전을 다시 맞췄습니다.
어느 날 한 기능을 배포하는 데 하루가 걸렸습니다. 코드가 아니라 저장소 사이의 의존성 동기화에 걸린 시간이었습니다. 그때 팀원 몇 명이 같은 이야기를 꺼냈습니다. "이 과정을 줄일 방법이 있지 않을까요?"
## 모노레포를 고른 이유
저장소를 계속 나누고 패키지 레지스트리로 연결하는 방법도 검토했습니다. 그래도 모노레포를 고른 이유는 다음과 같습니다.
- **원자적 변경**: API 응답 형식을 바꾸는 PR에서 클라이언트 코드도 함께 고쳐야 했습니다.
- **공유 코드의 즉시 반영**: 공통 라이브러리를 수정하면 버전 배포 없이 앱에 반영되어야 했습니다.
- **도구 통일**: 프로젝트마다 따로 관리하던 린트, 테스트, CI 설정을 한 곳에서 관리하고 싶었습니다.
모노레포에도 비용이 있습니다. CI 실행 시간이 길어지고 저장소가 커지며, 디렉터리별로 접근 권한을 나누기 어렵습니다. 그래서 옮기기 전에 이 비용을 감수할 만한지부터 확인했습니다.
## 옮기기 전에 한 일
1. **의존성 그래프 그리기**: 어떤 패키지가 어떤 패키지를 참조하는지 표로 정리했습니다. 예상하지 못한 순환 참조가 있어서 이것부터 끊었습니다.
2. **변경 빈도 조사**: 최근 6개월 커밋 기록에서 여러 저장소가 같은 시기에 함께 바뀐 경우가 많았습니다. 저장소를 하나로 묶어도 실제 작업 흐름과 어긋나지 않는다고 판단했습니다.
이 단계에서 팀 전체가 원칙 두 가지에 합의했습니다. 히스토리는 `git subtree`로 보존하고 기존 저장소는 한 달 동안 읽기 전용으로 남겨 둡니다.
## 옮기는 과정
- **1단계**: 공통 라이브러리를 `packages/`로 옮기고, 기존 저장소에서 참조하도록 설정했습니다.
- **2단계**: API 서버와 웹 앱을 `apps/` 아래로 옮겼습니다. 이때 CI 파이프라인이 변경된 패키지만 빌드하도록 바꿨습니다.
- **3단계**: 기존 저장소를 정리하고 문서와 배포 절차를 새 구조에 맞췄습니다.
단계마다 끝난 뒤 배포를 한 번씩 확인했습니다. 여러 단계를 한꺼번에 바꾸면 문제가 생겼을 때 어느 변경이 원인인지 찾기 어렵기 때문입니다.
## 겪은 문제들
**CI 시간이 늘어났습니다.** 처음에는 변경이 있을 때마다 모든 테스트가 돌았습니다. 바뀐 패키지와 그 패키지에 의존하는 패키지만 테스트하도록 바꾸자 평균 빌드 시간이 크게 줄었습니다. 팀 내부 측정 기준이 달라 구체적인 수치는 적지 않았습니다.
**버전 관리 방식을 정해야 했습니다.** 패키지마다 버전을 따로 올릴지, 저장소 전체에 버전 하나를 쓸지를 두고 논의가 길어졌습니다. 결국 내부 패키지는 버전 없이 워크스페이스 링크로 참조하고, 외부에 배포하는 패키지만 버전을 따로 관리하기로 했습니다.
**코드 소유권이 흐려졌습니다.** 한 저장소에 여러 팀의 코드가 섞이자 PR마다 리뷰어를 누구로 지정할지 헷갈렸습니다. `CODEOWNERS` 파일에 디렉터리별 담당자를 적어 두었습니다.
**옛 습관이 남았습니다.** 공통 라이브러리를 가져다 쓰지 않고 코드를 복사해 쓰려는 팀원이 있었습니다. 도구로 막을 수 있는 문제가 아니어서 이유를 설명하고 코드 리뷰에서 바로잡았습니다.
## 얻은 것
가장 크게 바뀐 것은 작업 흐름입니다.
- API와 클라이언트를 한 PR에서 함께 고칩니다.
- 공통 코드 수정이 바로 반영되어 버전을 맞추는 작업이 없어졌습니다.
- 린트와 테스트 설정을 한 곳에서 관리합니다.
- 새로 합류한 팀원이 저장소 하나에서 전체 구조를 파악합니다.
## 아쉬운 점
저장소가 커지면서 로컬 클론과 IDE 인덱싱이 느려졌습니다. 빌드 도구 설정을 이해하는 사람이 몇 명뿐이라는 문제도 있습니다. 두 문제 모두 아직 개선하는 중입니다.
## 마치며
우리가 원한 것은 변경을 빠르고 안전하게 배포하는 것이었고, 모노레포는 그 목표에 맞았습니다. 결정에 근거가 된 자료는 옮기기 전에 정리한 저장소 사이의 의존성 그래프와 6개월 치 변경 기록이었습니다.
