# 우리 팀이 모노레포로 옮긴 이야기

> 읽는 시간: 약 7분
여러 레포지토리로 나뉘어 있던 우리 서비스를 모노레포 하나로 합쳤습니다. 옮긴 이유, 옮긴 방법, 옮긴 뒤 달라진 점을 순서대로 적었습니다.
> `[대괄호]`로 표시된 부분은 우리 팀의 실제 숫자와 이름으로 바꿔 주세요.
## 1. 레포가 나뉘어 있을 때의 문제
옮기기 전 우리는 `[N]`개의 레포지토리를 운영하고 있었습니다.
- `web` — 프론트엔드
- `api` — 백엔드 서버
- `shared-types` — 공통 타입 정의 (npm 패키지로 배포)
- `ui-kit` — 공통 UI 컴포넌트 (npm 패키지로 배포)
- `infra` — 배포 및 인프라 설정
처음에는 레포가 나뉘어 있는 게 깔끔해 보였지만, 팀이 커지면서 아래 문제가 반복되었습니다.
### 1.1 작은 변경 하나에 PR이 세 개
API 응답 필드 하나를 추가하려면 이런 순서를 밟아야 했습니다.
1. `shared-types`에 타입 추가 → PR → 리뷰 → 머지 → 버전 올려 배포
2. `api`에서 새 버전을 설치하고 구현 → PR
3. `web`에서 새 버전을 설치하고 화면 반영 → PR
변경 자체는 10분이면 끝나는데, 레포 사이를 오가며 기다리는 시간이 하루를 넘기곤 했습니다.
### 1.2 버전 불일치
`web`은 `shared-types@1.4.0`, `api`는 `1.3.2`를 쓰고 있는 상황이 종종 생겼고, 이런 문제는 런타임에서야 드러났습니다.
### 1.3 레포마다 다른 설정
ESLint, TypeScript, CI 설정이 레포마다 조금씩 달랐습니다. 처음에는 같은 설정을 복사해 시작했지만, 레포마다 따로 고치면서 차이가 생겼습니다.

| CI 시간이 길어지지 않을까? | 변경된 패키지만 빌드/테스트하도록 구성하면 해결 가능 |
| 레포가 너무 커지지 않을까? | 현재 규모에서는 문제 없음. 커지면 그때 다시 논의 |

| 마이그레이션 중 개발이 멈추지 않을까? | 단계적으로 옮기고 그동안 기존 레포도 유지 |

## 3. 이렇게 옮겼습니다
### 3.1 디렉터리 구조
`pnpm-workspace.yaml`은 이렇게 간단합니다.
### 3.2 git 히스토리 보존
히스토리를 버리고 파일만 복사하면 `git blame`과 과거 커밋 맥락이 사라집니다. 그래서 각 레포의 히스토리를 하위 디렉터리로 옮긴 뒤 병합했습니다.
> `git filter-repo`는 별도 설치가 필요합니다. 실행 전에 반드시 **클론한 사본**에서 작업하세요.
### 3.3 내부 패키지 참조
버전을 올려 배포하던 방식을 워크스페이스 참조로 바꿨습니다.
이제 `shared-types`를 수정하면 `web`과 `api`에 즉시 반영됩니다. 배포도, 버전 올리기도 필요 없습니다.
### 3.4 변경된 부분만 빌드하기
`turbo.json`으로 작업 간 의존성을 선언했습니다.
CI에서는 변경에 영향받는 패키지만 실행합니다.
### 3.5 단계별 전환
한 번에 모두 옮기지 않고 아래 순서로 진행했습니다.
1. **공통 패키지부터** — `shared-types`, `ui-kit`
2. **백엔드** — `api`
3. **프론트엔드** — `web`
4. **인프라** — `infra`
5. 기존 레포는 읽기 전용으로 전환 후 아카이브
각 단계마다 최소 `[N]`일은 안정화 기간을 두었습니다.
## 4. 겪었던 문제들
### 4.1 CI에서 캐시가 적용되지 않음
처음 며칠은 매번 전체 빌드가 돌았습니다. CI 환경에서 캐시 디렉터리를 저장·복원하지 않은 것이 원인이었고, 원격 캐시를 붙인 뒤에야 의도한 속도가 나왔습니다.
### 4.2 의존성 호이스팅 문제
pnpm은 의존성을 엄격하게 분리하기 때문에, 선언하지 않고 쓰던 패키지가 한꺼번에 에러로 드러났습니다. 고치는 데 손이 많이 갔지만, 그동안 선언이 빠져 있던 의존성을 이때 정리했습니다.
### 4.3 커밋 컨벤션과 릴리스
여러 앱이 한 레포에 있으니 "이 커밋이 어느 앱에 영향을 주는가"가 중요해졌습니다. 커밋 스코프(`feat(web): ...`, `fix(api): ...`)를 규칙으로 정했습니다.
## 5. 결과
옮기고 나서 `[기간]` 동안 지켜본 변화입니다.
| 항목 | 이전 | 이후 |
| 타입 변경이 포함된 기능 PR 수 | 평균 `[N]`개 | 1개 |
| 변경 → 모든 앱 반영까지 걸리는 시간 | `[N]` | `[N]` |
| CI 평균 소요 시간 | `[N]`분 | `[N]`분 |
| 공통 설정 불일치로 인한 이슈 | 월 `[N]`건 | 월 `[N]`건 |
표에 담기지 않은 변화도 있습니다.
- 레포 경계에서 멈추지 않는 리팩터링
- 새로 합류한 사람이 클론 한 번으로 전체 구조 파악
- "이 패키지 어느 버전 쓰고 있어요?"라는 질문이 더 이상 나오지 않음
## 6. 모노레포가 맞는 팀과 맞지 않는 팀
**추천하는 경우**
- 레포 간 공통 코드(타입, 컴포넌트, 유틸)가 많다
- 하나의 기능이 보통 여러 레포를 동시에 건드린다
- 같은 팀이 대부분의 레포를 함께 관리한다
**신중해야 하는 경우**
- 레포별로 팀과 배포 주기가 완전히 독립적이다
- 접근 권한을 레포 단위로 엄격히 나눠야 한다
- 빌드 도구와 언어가 서로 전혀 다르다
우리 팀은 추천하는 경우에 해당해서 잘 맞았습니다. 신중해야 하는 경우에 해당하는 팀에는 맞지 않을 수 있습니다.
